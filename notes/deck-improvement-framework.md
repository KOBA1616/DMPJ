# デッキ自動改善の枠（設計と記録）

計画書 v2.8 の §4.7（計画仕様 v0）と §3.3（評価セットの更新規則）に合わせた、拡張用の枠。**エンジン（dmsim/engine/）とカードデータ（data/cards/）には触れない**。reject 解消の作業と競合しない。

## 構成（dmsim/deckplan/）
| ファイル | 役割 |
|---|---|
| spec.py | デッキ案の記録形式。カード名は人の表記のまま、ID は後で確定。スキーマ版つき、未知項目は保持、タグは複数可（単一ラベル分類にしない）。`check` は枚数・4枚上限を検査し、未変換/未解決カードを含むデッキを `unverified` にする。 |
| change.py | 変更案（提案側）。`@proposer("kind")` で登録式。いまは swap のみ。探索・学習による提案は同じ登録に足す。 |
| evaluate.py | 採否。測るのは dmsim.eval のハーネス（`harness_scorer`）。`AcceptRule` は凍結した版つき（指標=Nターン目までのキル率、FAIRのみ、同一シード・先後の対比較）。未確認デッキは `hold_unverified` で自動採用しない。結果は追記専用の jsonl に記録。 |
| loop.py | 提案 → 評価 → 採否 → 記録の最小ループ。 |

## 変えないもの（人だけが変える）
指標、採否の規則、信頼区間の設定、評価セット（§3.3-5）。自動化するのは変更案の生成と記録だけ。

## 接続点
- 評価: `harness_scorer(rules, opp_deck, seeds)` が `run_eval` を呼ぶ。相手モデルや開始局面は `EvalConfig` の引数をそのまま渡せる。
- 探索側（dmsim/search/）: 提案側の proposer から呼ぶ。枠は探索の中身を知らない。
- カード解決: `Resolver(Entry)->(card_id, 状態)` を差し替える。変換が済むまでは `unresolved` で、デッキは「未確認」。

## 記録したデッキ案
`data/deckplans/mono_red_beatdown_v0.yaml`: 火単ビート案（10種×4枚）。ID は未確定。koba 確認済み: ブレイズクローは凶戦士ブレイズ・クロー、入れるのは“罰怒”ブランド(未変換、master_bad。1st は別カード)。ID は変換後に入れる。

## 未実装・次
カード解決の実装（変換完了後）、pool の選び方（相補的なカードの候補）、複数の変更を組み合わせる提案、計画IDの経験ログ連携（§4.7-9）。
