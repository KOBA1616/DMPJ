# 全保持探索からの鎖生成と最適化の自動化: 追加実装の設計

作成: 2026-11-18
位置づけ: docs/chain-automation-system.md の追加実装。鎖の生成材料を
キル記録から全保持（frontier）探索の結果へ広げ、生成後の最適化までを
自動化する。関連: docs/phase-chain-plan.md（段1・段2 の試作と実測）、
docs/frontier-disk-design.md（ディスク常駐・分割実行）。

---

## 1. なぜ全保持探索から生成するか

現行の抽出器（tools/chain_extract.py）は検証済みのキル記録を材料にする。
サガでは11件で足りたが、構造的な弱さがある:

- 材料は勝ち軌跡だけ（各1本の線）で、負例がない。通過点の条件が
  「勝ち筋に共通」でも「死に筋も満たす」ものか区別できない。
- 標本が少なく閾値が不安定。キルターン開始時点で未所持の部品は
  条件から抜ける（ドラゲリオンの手札条件が入らなかった実例）。
- 記録のないコンボ・デッキでは材料自体がない。

全保持探索は、ターン境界の到達局面の全体と、その後の探索結果を
持っている。完走した探索では各局面に「あと何ターンで殺せるか」を
付けられる（§2）。勝ち・負け両方のラベルつき局面集合は、記録の
集合より桁違いに大きな標本であり、閾値と通過点の根拠が安定する。
探索は検証のためにどのみち回すので、材料はその副産物になる。

## 2. 追加実装1: ラベル付け（chain_label）

新しい道具 `tools/chain_label.py` として実装する（既存の
exhaustive_crossturn は変更しない。内部部品 — LeafCollector、
状態ストア、advance_to_my_turn、段の候補生成 — を import して使う）。

通常の探索との違いは2つ:

1. **最初のキルで止めない**。frontier を最大ターンまで全て展開し、
   局面ごとに「その展開の中でキル葉が出たか」と「次ターンの子局面の
   キー集合」を記録する（edges として追記保存）。
2. **ラベルの後方伝播**。全展開の後、最終ターンから逆向きに
   dist（最速キルまでの残りターン）を計算する:
   - その局面の展開でキルが出た → dist = 1
   - 子の最小の dist が d → dist = d + 1
   - 到達できるキルがない → dist = ∞（範囲内での死に筋）

出力: 状態ストア（局面の実体）＋ edges ＋ labels（キー → {turn, dist}）
＋実行条件の記録。実行はディスク常駐・分割実行の流儀を踏襲し、
目録で中断・再開できるようにする。

ラベルの正直さ:

- 保持上限・葉上限・局面毎予算の打ち切りがある枝では dist は
  確定しない。打ち切りに触れた局面とその祖先は「ラベル不確実」として
  印を付け、抽出の材料から外す。
- dist = ∞ が「証明された死に筋」になるのは、打ち切りなしで
  完走した場合だけ。それ以外は「範囲内で未発見」として扱う。

## 3. 追加実装2: 抽出器 v2（chain_extract2）

入力をキル記録から「ラベルつき局面集合」に替える。通過点と閾値の
決め方は現行の規則を、標本だけ大きくして適用する:

- 候補の特徴はデータから列挙する: 各ゾーンの "*" 枚数と、
  各カードのゾーン別枚数。
- dist ≤ d の局面が**全て**満たす条件を、その水準の通過点とする
  （枚数条件は最小値を閾値にする）。dist が大きい局面ほど手前の段に
  なるよう並べ、累積形に直すのは現行と同じ。
- 負例でふるいにかける: dist = ∞ の局面も多数満たしてしまう条件は
  弁別力がないので弱める／外す（記録だけの抽出ではできなかった判定）。
- 生成物には根拠を併記する: 材料の実行（ケース・設定ハッシュ）、
  ラベル確定した局面数、各段の支持数（dist ≤ d の何件が満たすか）。

フェーズ分けはラベルが与える: dist の大きい局面の通過点が
部品集め、小さい局面の通過点が実行・仕上げの段になる。

## 4. 追加実装3: 最適化ループ（chain_optimize）

生成→ゲート→調整→再生成を自動で回す:

1. 抽出器 v2 で候補の鎖を生成する（パラメータ違いで複数候補）。
2. 各候補を鎖ゲート（tools/chain_gate.py: 診断＋保持テスト）で測る。
3. 落ちた候補は調整ノブを変えて再生成する。ノブは:
   - 閾値の取り方（最小値／分位＋余裕）
   - 特徴の集合（ゾーン "*" のみ／カード別枚数も使う）
   - 段の粒度（水準ごとの分割／統合）
   - 負例フィルタの強さ
4. 目的は多目的: 診断順位、保持テストの成否、ノード数、そして
   **鎖の単純さ**（段が少なく条件が粗い方を優先する）。

過適合への歯止め（必須の組み込み条件）:

- **ホールドアウト**: 最適化に使うケースと検証に使うケースを分ける。
  材料の探索（例: doom_e のデッキケース）とは別のシナリオ
  （hidden / prep）でゲートを通すのは現行ゲートの形そのもので、
  この分離を崩さない。材料と同じケースでの診断は参考値に留める。
- **単純さの優先**: 同程度の成績なら単純な鎖を採る。細かい条件の
  積み増しでゲートだけを通す鎖を作らない。
- **反復の上限**: 調整の反復回数と総計算量に上限を置き、上限での
  最良候補と全試行の記録を残す（勝った候補だけを残さない）。

## 5. 実装の順序と検証

1. chain_label を実装し、小ケース（prep seed1、最大2ターン）で
   検証する: ターン1の開始局面の dist が 2、キルに届くターン2局面の
   dist が 1 になること。既存のキル記録と矛盾しないこと。
2. chain_extract2 を実装し、prep のラベルから生成した鎖を
   鎖ゲートに通す。現行の抽出チェーン（記録11件・PASS）と比較する。
3. デッキケース（doom_e seed24 等、frontier 実行済み／実行予定の
   ケース）でラベル付けし、生成した鎖で plan trim の保持テストを
   行う（汎化の判定基準: frontier のキルターンを beam のコストで
   再現できるか）。
4. chain_optimize を実装し、ホールドアウト込みで回す。

## 6. 制約と注意

- ラベル付けは全保持の全展開が前提なので、コストは frontier 実行
  そのもの。母集団コストの実測（時間の検証）と無関係ではない:
  ラベル付けは「証明のための frontier 実行」の副産物として回すのが
  基本で、鎖生成のためだけに大きな frontier を回すのは最後の手段。
- 実行中の探索がある間は exhaustive_crossturn.py を変更しない
  （分割実行の再開条件＝エンジン版が変わるため）。本追加実装は
  新規ファイルで完結させ、この制約を避ける。
- dist の伝播は「無抵抗・固定シード」の範囲内の話である。通常の
  探索の判定と同じ前提を引き継ぐ。
