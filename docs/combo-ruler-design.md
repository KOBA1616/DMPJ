# コンボを測る物差しの設計（P2 最初のタスク、2026-11-13 案）

状態: **v1（2026-11-13 確定、未実装）**。§6 の順で実装する。決定事項は §7。

## 0. この物差しが測るもの

「ある札の組が、コンボとしてどこまで進めるか」。進み具合を次の4つの目盛りで、**別々に**測る（1つの点数に混ぜない）。

| 目盛り | 一言で | 開始局面 | 主に効くもの |
|---|---|---|---|
| ① 揃う | 通常の開幕から部品が揃う確率と、揃うターン | 通常の開幕（40枚・シャッフル） | デッキ |
| ② 段1 ループ成立 | 効果を何回でも蓄積（ストック）できる状態に入れるか | 仕込み局面（部品が揃った状態） | 札の組そのもの・探索 |
| ③ 段2 勝利への変換 | 蓄積を転用・変換・拡大して、実際に勝てるか | 仕込み局面 | 札の組（勝ち手段を含む）・探索 |
| ④ 速さ | 通常の開幕から3〜4ターン目までに勝ちまで届く割合 | 通常の開幕 | 全部 |

考え方（koba さんの整理）: ループはコストに対するアドバンテージが無限。だから「コスト対アドバンテージ」は**ループかどうか**は分けられても、**ループ同士の優劣**は分けない。差が出るのは、その無限を勝ちに変えられるか（③）と、どれだけ早く揃うか（①④）。

目盛りは順に厳しくなる: ③に届いた組は②にも届いている。④は①×（②③の実行）の結果を通常の開幕でまとめて見たもの。

**信用できない数字**: combo_screen の点（#303 以降の opp_deck / opp_mana を含む）、ずるい探索や reach_rate を公平な値として扱ったもの。

## 2. 各目盛りの定義

共通の入力: **札の組**（部品の札 ID と必要枚数）、**デッキ**（40枚。①④で使う）、**開始局面の作り方**（②③。既定は exec_tier の決め方）、**相手**（既定は今と同じ「マナチャージだけ」の相手。相手デッキはダミー40枚）、**seed の一覧**、**ターン上限**。設定はすべて結果と一緒に記録する（§3 登録簿）。

### ① 揃う
- 数えるのは**中核の札だけ**（§9）。サーチ・ドロー・加速などの基盤札は数えない。
- 観測: 通常の開幕から公平探索で回し、自分の各ターン終了時に「中核の部品が山札・盾以外の自分のゾーンに揃ったか」（今の cards_met と同じ意味）。
- 出力: 揃った割合（T=3, 4, 6 ごと）と揃ったターンの分布。並べて素引き確率（下限の理論値）も出す。
- 判定: 数値のみ（合否なし）。実測が素引きより大きく下なら「探索が部品を使い損ねている」の印。

### ② 段1 ループ成立
仕込み局面から探索で回し、エンジンが出すループ証明書を見る。**次を全部満たした証明書が1つでも出たら到達**。段1は**相手の残り資源と無関係に**判定・記録する（勝ちに足りるかは段2で見る）。

1. **再生で確認済み**: 証明書の行動列を2周再生して、同じ骨格・同じ差分に戻る（今の verify）。
2. **回数 N を記録する**（合否には使わない）: N = 自分の資源の消費だけで決まる「繰り返せる回数」（今の analyze の limit。相手側は見ていないことをコードで確認済み）。自分の山札を消費するループは山札1枚を残して数える。
   - N = ∞ … 「無限ループ」（自分の資源を減らさない）
   - N が有限 … 「有限ループ（N 回）」
   - N = 0 は1周もできないので不成立。
3. **ストックがある**: 1周の差分のどれかが「蓄積できる資源」の増加か相手資源の減少である。
   - 自分の得: 手札・アンタップのマナ・場の数・盾の下の枚数・墓地（再利用札がある時）の増加
   - 相手の損: 相手の山札・盾・マナ・場・手札の減少
   - 自分の山札だけが減るループ（サガ型）も、③で勝ち手段に使えるなら「ストックあり」とする（今の is_burn）
   - 自分の他の資源が周回ごとに減るものは「ストックなし」（上限が有限になるので2.で落ちる）
4. **ストックの数え方**: 1周ごとの差分ベクトル（資源ごとの増減）と limit を記録する。**周回数で数え、資源の価値に換算しない**（ループ同士の優劣はここで付けない）。

出力: 到達したか、到達した自分のターン、証明書（種類 = 相手を削る／自分の資源を増やす／自分の山札を削る、1周の差分、N）。

**記録の例（サガ型）**: 仕込み局面の実測（§8）では、証明書は「種類=自分の山札を削る、1周の差分=自分の山札 −1、N=5」。段1は「有限ループ（5回）」で到達。勝ちに足りるか（シャコガイルの勝利条件まで山札を減らせるか）は段2で見る。

### ③ 段2 勝利への変換
②に届いたあと、同じ局面からゲームを続けて**実際に勝ったか**を見る。勝ちの判定はエンジン（S2）の結果をそのまま使う。

到達の条件（どれか1つ）:
- **山札切れ勝ち**: 相手の山札が0枚になり、相手がドローして負けた（エンジンの終局）。
- **盾全破壊からの勝ち**: 相手の盾0枚の後、ダイレクトアタックが通って勝った。
- **効果での勝ち**: 勝利条件の効果（シャコガイルの置換など）で勝った。
- **ロック勝ち（ターンをまたぐ）**: **独立の勝ち方としては数えず、「山札切れ勝ち」の経路の1つ（経路=ロック）として記録する**。エンジンの勝ち判定は最終的に相手の山札切れなので。判定は、自分が何もしなくても相手は資源が増えず、山札切れまで何もできない（今の lock_probe ＋ lock_ok）。**加えて**、ロック確立後も実際に相手の山札切れまで回し、**自分が先に山札切れで負けないこと**を確かめる（今は確立時点で打ち切っているので、ここを足す）。両者同時の山札切れはターンプレイヤーの負け（ルール判断どおり）。

条件（どれでも共通）:
- その勝ちが**②のループを使ったもの**であること（証明書が出た後の勝ちで、ループの周回を実際に使った。今の origin が loop / engine / lock）。ループなしの殴り勝ちは③に数えない（別に記録する）。
- 自分の山札切れで負けていないこと。

- **N が勝ちに足りるか**はここで判定する: 段1の N と1周の差分から、勝ちに要る周回数（今の needed）が N 以下か。足りなければ「段1到達・段2未到達（回数不足）」と理由を残す。

出力: 到達したか、勝ち方（山札切れ〔経路: ループで削る／ロック〕／盾／効果）、勝ったターン、使った周回数。

### ④ 速さ
- 観測: 通常の開幕から**公平探索**（山札は見えない）で回す。
- 出力: 自分の3ターン目まで・4ターン目までに③の勝ち（またはループを使わない勝ちも別欄で）に届いた割合。95% 信頼区間（Wilson）つき。
- 先攻・後攻は seed の偶奇で半々。

### 打ち切り条件（②③④共通）
- ターン上限（②③は仕込み局面から自分の3ターン、④は自分の4ターン。設定で変えられるが、結果に必ず記録）。
- 探索予算（ノード数）。
- ロック確認の延長は「相手の山札切れまで、ただし最大で相手の山札枚数＋2ラウンド」。
- 打ち切った局は「未到達」とし、理由（ターン上限／予算／自分の負け）を残す。

## 4. 陽性対照（物差しの校正）

目的は「物差しが正しいか」の確認。既知の強いコンボがランダムな組より上に来ない物差しでは、未知のコンボを見つけても信用できない。

- **入力にする既知コンボ（tuning）**: サガ、騎士＋DMC、アカシック。勝ち手段まで含めた組を `data/known_combos/combos.yaml` から渡す。天門は開発中止なので除く。**ドリル＋ジョバンニは検証専用（holdout）のまま、校正の判定に使わない**（結果は参考表示だけ）。
- **開始局面**: exec_tier の決め方で作った仕込み局面（部品が揃った状態）。
- **ランダムな組**: 同じ仕込み局面の**中核の部品（core）だけ**を、同じ種類（クリーチャー／呪文）・近いコストの無作為なカードに差し替える。補助札（support）・マナ・盾はそのまま。1コンボにつき 20組。
- **合格条件**（全部満たす）:
  1. 既知コンボ3つとも、③（段2）の到達率が 0.8 以上（騎士＋DMC・アカシックは実行層 1.00、サガ 0.85 の実績から）。
  2. ランダムな組の③到達率の中央値が 0.05 以下。
  3. 既知コンボの③到達率が、ランダムな組の分布の上位5%より上（今の validity.judge の percentile 判定と同じ）。
  4. ②でも同じ順序（既知 > ランダム）になっている。
- **張り付き検知**: 全行同値、または既知コンボとランダム組が同値なら、理由つきで不合格（validity.judge をそのまま使う）。物差しを変えたら必ず対照を回し直し、合格の印（指紋つき）を登録簿に残す。印のない物差しの結果は「採用不可」。

## 6. 実装タスク（1タスク1PR、順序つき）

1. **陽性対照用の仕込み局面**: サガ・騎士＋DMC・アカシックそれぞれに「ループの入口」の開始局面を用意する（data/loops の LoopSpec を使う）。殴り勝ちより先にループを使う局面であることを、今の play_game で確かめる（§8）。
2. **ロック判定を S4 へ移す**: lock_probe / round_probe / lock_ok を `dmsim/eval/lockcheck.py` へ。play_game は判定役を引数で受ける（既定は今と同じ動き）。旧名は別名で残す。同一シード一致を確認。
3. **ロック勝ちの最後までの確認**: ロック確立後、相手の山札切れまで回して自分が先に尽きないかを確かめる関数を足す（既定ではまだ play_game に組み込まない）。
4. **探索のループ記録を「選んだ手順」に絞る**: いまの `search/turn.py` はストック候補を作るたびに記録し、選ばなかった枝の分も混ざる。実際に採った手順に入ったループだけを GameResult に残す（候補の記録は別名で残す）。同一シードで勝敗が変わらないことを確認。物差しの段1はこの記録を使う。
5. **物差しの本体 `dmsim/eval/ruler.py`（段1・段2）**（済み、§8.4）: 仕込み局面から回して、段1（再生確認・回数 N・ストック）と段2（N が勝ちに足りるか・勝った瞬間の勝ち方がループの蓄積由来か・自分の山札切れなし）を判定し、ループ勝ちと殴り勝ちを別欄で返す。単体テストは小さな手作りの局面で。
6. **揃う・速さを ruler に載せる**（済み、§8.5。`dmsim/eval/assemble.py`）: 既存の progress（cards_turn、中核だけ）・reach と、run_eval の FAIR セルを呼んで同じ形で返す。キル率は殴り勝ちを含めて数え、ループ勝ちを別欄に出す。
7. **登録簿への記録**: S0 の書き込み口に測定結果と指紋を書く。
8. **陽性対照（校正）**: §4 の手順（1 の開始局面、中核だけ差し替えたランダム組、0.8 / 0.05）を `tools/ruler_control.py`（仮）と `tests/test_measure_control.py` に。合格の印を登録簿へ。
9. **目標値の集計**: §5 の3つを1つの表で出すツール。日次ルーティンから呼ぶのはこの後に判断する。

## 8.3 ループの記録の形（2026-11-13、タスク4で実装）

`GameResult.loops` は**採った手順で使ったループだけ**。探索が試した候補（選ばなかった線を含む、旧 `loops` の中身）は `GameResult.loop_candidates`。`TurnSearch` は `_search` の戻り値に「その葉に至る線で使ったループ」を持たせ、最善の線のものだけを `TurnStats.chosen` に入れる（`TurnStats.loops` は候補のまま）。勝敗・手順は変わらない（同じ評価で同じ葉を選ぶ）。

1件の欄（共通）: `source`（`certificate`＝ループ証明書／`pattern`＝実際の手順の繰り返し）、`verified`（True。証明書は verify 済み、pattern は実際に N 周指した）、`kind`、`delta`（1周の差分、`ゾーン:プレイヤー`）、`stocked`（回した周回数 N）、`length`（1周の手数）、`win_by`、`needed`、`own_turn`。
- certificate: `limit`（`inf` なら無限）。
- pattern（サガ型の有限ループ、`dmsim/search/pattern_loop.py`）: `kind: finite`、`infinite: False`、`laps`（= stocked）、`stock`（delta×laps）、`limit_est`（減る資源が尽きるまでの見積もり。確かめていない）、`log_start`/`log_end`（eng.log の位置。勝ちの瞬間 `len(log)` と比べて「勝ちに使われたか」の材料）、`lap_actions`、`anchor`。

pattern の検出条件（誤検出対策）は `pattern_loop.py` の冒頭: 手札・山札の札の種類は問わず、それ以外の鍵は完全一致で3周以上／毎周、墓地・場・マナの同じ札（錨）を選ぶ／1周ごとの枚数差分（両者の各ゾーンと未タップのマナ）が全周で同じ／自分について差分が0でない／そのターンに証明書のループを採っていれば調べない。
`origin()` は pattern も数える（ループの後の殴り勝ちは `engine`）。

## 8.2 ロック勝ちを最後まで回した結果（2026-11-13、タスク3）

`dmsim/eval/lockcheck.py` に `run_lock_to_end`（結果 `LockRun`: 成立ターン・勝ちまでのターン数・自分の山札残り・破れた理由とターン）、能動ロック用の自分の方針 `prefer_policy`、`play_game(lock_judge=...)` に差し込める `make_full_lock_judge` を足した。play_game の既定の判定役は lock_probe のまま。
破れの判定は「自分のターン開始時の相手資源（山札・墓地以外）が、成立の一巡後より増えたら破れ」。

**ドリル＋ジョバンニで lock_probe が None だった原因**（検証専用、調整には使っていない）:
1. lock_probe は「自分が何もしない」ロックしか見ない。ドリル＋ジョバンニは毎ターン自分がドリルを唱える**能動ロック**なので、設計上検出できない。
2. passive の方針は「好きな枚数」の選択で最小（0枚）を選ぶので、ジョバンニがドリルを手札に戻さない。構造が残っていても回らない。
3. 探索（play_game、6ターン）もドリルを唱える手を選ばず、相手マナは 6→8 に増えた。
4. ドリル1枚・毎ターン1回では相手マナは**減らず開始枚数のまま固定**される（setup_from_cycle の既定 opp_mana=6 なら6のまま）。マナチャージだけの相手モデルでは山札切れまで勝てるが、実戦の「マナ0ロック」ではない。
5. 自分の方針に「ドリルを唱える・戻す・マナに置いたダミーを墓地へ・ダミーをチャージ」を与えると、自分の25ターン目に相手の山札切れで勝ち、自分の山札残りは1枚（ぎりぎり）。文明の札を墓地へ送る方針では途中で唱えられなくなり破れる。

**タスク5への注意**: 能動ロックを段2に数えるには、ロック中の自分の方針（探索または prefer_policy）を判定役に渡す必要がある。lock_probe 単独の None は「ロックでない」ではなく「受け身のロックでない」。

## 8.4 物差しの本体（2026-11-13、タスク5で実装）

`dmsim/eval/ruler.py` の `judge(res, eng, *, lock_mode="passive")` が play_game の (GameResult, Engine) を読み、`Verdict(stage1, stage2, reason)` を返す（`to_dict()` で辞書）。記録を読むだけで、測定の挙動は変えない。

- **段1** `Stage1`: `ok`・`n_loops`・`verified`・`infinite`（certificate の limit=="inf"）・`n`（certificate は stocked、pattern は laps。最大のループ）・`limit_est`（pattern の見積もり、別欄）・`delta`（1周の差分）・`stocked`・`sources`・`reason`。採った手順の `loops` だけを見る（`loop_candidates` は理由文に件数を出すだけ）。
- **段2** `Stage2`: `ok`（ループかロックで勝ち、かつ自分の山札切れなし）・`engine_win`・`win_kind`・`win_turn`（自分の何ターン目）・`via`（loop / lock / beat / other）・`loop_win`・`beat_win`・`kill`（キル率に数える勝ち。beat と other も含む）・`self_deck_out`・`attacks_after_loop`・`lock`（`mode` passive/active、`opp_mana`、`opp_mana_zero`）・`reason`。
- **勝ち方の分類**: direct_attack は常に beat（ループの後でも）。loop_deck_out、または勝ちのターンに相手の山札を減らすループがある deck_out は loop。effect / state は、勝ちのターンに勝ちより前に終わったループ（pattern は log_end ≤ 勝ち時点の len(log)）があれば loop。それ以外の勝ちは other。ロックは lock（山札切れ勝ちの経路）。受け身か能動かは呼び出し側が渡した判定役で決まるので `lock_mode` で受ける。
- **certificate のログ位置は足していない**: 今の certificate は「勝ちのターンに使ったか」（own_turn）で足りた（アカシックは loop_deck_out で win_by も付く）。effect 勝ちの certificate が出たら、`search/turn.py` で log 位置を足す。

## 9. 中核と基盤、アドバンテージの扱い（koba さんの質問への回答）

**中核と基盤を分ける**
- 札を「**中核**」（ループの部品と勝ち手段）と「**基盤**」（サーチ・ドロー・マナ加速などのリソース拡充札）に分ける。
- 物差しの①揃うは**中核だけ**を数える。基盤を部品に含めると組の数が莫大になるため。
- 基盤は、中核を固定したうえで、①揃うと④速さへの効き目で選ぶ（S5 デッキ構築の責務）。探索は中核の組を探し、基盤は後から足す2段構えなので、**中核×基盤の掛け算にはならない**。

**アドバンテージ獲得の評価**

## 12. 陽性対照（校正）の実測（2026-11-13、タスク8）

道具: `dmsim/eval/ruler_control.py`（判定 `judge_control`、印 `status`）、`tools/ruler_control.py`（実行。`--stamp` で `data/eval/ruler_control_stamp.json`、コミットしない）。単体テスト `tests/test_ruler_control.py`。

**入口局面のばらつき**（`vary`）: 場・墓地・マナと、入口 M が手札に要求する札はそのまま。手札の残りと盾を山札の残りと混ぜてシードで配り直し、山札の並び、相手の山札枚数（±3）も変える。8シードで開始局面は8種（指紋 `start_key` で確認）。

**ランダムな対照組**（`make_randoms`）: ループの部品（入口 M が名前で要求する札。サガ: シャコガイル・サガ、アカシック: アカシック3・ナウ・オア・ネバー・ウォカンナ・オルゼキア）を1種類選び、デッキと局面の全コピーを別の札1種類へ。置き換え先は同じ種別・コスト差1以内・文明を共有・非進化・既知コンボの中核でない札から、部品ごとに4枚。全部差し替えると自明に0になるので1種類だけ。マナ・盾に置いただけの中核（コダマ・イザナギテラス・フィオナ・モーニンジョー・ラルド）は、最初の実測で差し替えても結果が変わらなかった（1.00 が多い）ので対象から外した。

**合否と自己点検**: 既知ごとの段2到達率 ≥ 0.8、ランダム組の中央値 ≤ 0.05。全行同値（張り付き）、既知の開始局面がシード間で同じ（ばらつきなし）、ランダム組の最大が既知の最小以上（区別なし。中央値も超えれば不合格、そうでなければ警告）、対局の失敗、を理由付きで不合格。

実測（各8シード、上限2ターン、budget は入口の既定 サガ200・アカシック1500）:

| 対象 | 段2到達率 | 内訳 |
|---|---|---|
| サガ（既知） | **0.12** | loop 1 / beat 6 / 勝ちなし 1。budget 1000・3000 でも 0.50 |
| アカシック（既知） | **1.00** | すべて loop（loop_deck_out） |
| ランダム組（24組） | 中央値 **0.00**、最大 1.00 | サガ部品の差し替え8組はすべて 0。アカシック: アカシック3・オルゼキア差し替えは 0、ウォカンナ差し替えは 0.38〜0.88、ナウ・オア・ネバー→ルナ・ブライトホークが 1.00 |

**判定: 不合格**（サガが 0.8 に届かない）。見立て:
- サガ: **探索（S3）**。ばらつきの無い元の入口では 8/8 だが、手札に他の札（2枚目のシャコガイル、イザナギテラス、エマージェンシー・タイフーン等）が入ると、1ターン目にループを見つけず2ターン目に殴り勝つ。予算を増やすと 0.12→0.50 で頭打ち。ループの部品は全シードで揃っている。旧い「8/8」は1局面を8回測っていただけ。
- アカシックのウォカンナ差し替えで勝つ組・ルナ・ブライトホークで勝つ組: 物差しの緩さか、本当に別の部品で回るのかは未確認（loop_deck_out の勝ちなので段2の分類自体は正しい）。次に1局ずつ手順を読む必要がある。
- ランダム組の中央値は基準を満たす（物差しは部品の欠けた組の大半を落とせている）。

**旧い陽性対照ゲートとの関係**: 併存させる。`validity.judge` / `combo_screen --control`（data/eval/control_stamp.json）は変更しない（今も張り付きで不合格と出る）。旧い印を読むのは `combo_screen --verify` の `validity.annotate` だけで、日次ルーティン・監査・autofix は validity を使っていない（grep で確認）。よって挙動が変わる箇所はない。新しい印 `ruler_control_stamp.json` は validity と同じ指紋（dmsim/*.py とカードデータ）で失効し、今はどこからも読まれない。読む側（目標値の集計・日次）への接続はタスク9で決める。

## 13. 札を替えても勝つ組の正体（2026-11-13、§12 の続き）

§12 のアカシックのランダム組で段2に届いた組（ウォカンナ差し替え 0.38〜0.88、ナウ・オア・ネバー差し替えの一部 0.25〜1.00）を、1〜2シードずつ手順（eng.log の keys）で追った。

**判定: (a)＋(b)。物差し（ruler.py・pattern_loop.py）の不具合ではなく、カードデータ・エンジンの誤りでもない。** アカシックのデッキには、既知のループとは別の、より部品の少ない本物のループが入っていた。

- 既知のループ L1: アカシック3（場）＋ナウ・オア・ネバー＋訪れる魔の時刻×2＋ウォカンナ（相手の山札を1枚墓地へ）。
- 別のループ L2: アカシック3（場）＋訪れる魔の時刻×2＋**H.D.2.（ラルド・ワースピーダのツインパクト、デッキに4枚）**。H.D.2. を相手に向けて唱え（山札の上2枚を相手のマナへ）、訪れる魔の時刻で「もう1枚の訪れる魔の時刻（オルゼキアの面でクリーチャー）とラルド（クリーチャー）」を墓地から回収、をアカシック3の無償詠唱で繰り返す。証明書は無限（delta: 相手の deck −2・mana +2）、勝ちは loop_deck_out。ナウ・オア・ネバーは要らない。
- 手順の例: ウォカンナ→ハルカス・ドロー、seed 1（自分1ターン目に L2 で勝ち）。ナウ・オア・ネバー→ルナ・ブライトホーク、seed 1（2ターン目に H.D.2. を手で唱え、以後 L2。最初は自分向き mode 0 でマナを伸ばし、後半に相手向き mode 1）。
- ルール照合: 訪れる魔の時刻「好きな数のクリーチャーを、自分の墓地から手札に戻す」。ツインパクトは墓地でクリーチャーでもあるので、オルゼキア／訪れる魔の時刻とラルド／H.D.2. を戻せる。H.D.2.「プレイヤーを１人選ぶ。そのプレイヤーは、自身の山札の上から２枚をマナゾーンに置く」はデータの modal（自分／相手）と一致。アカシック3「自分は呪文をコストを支払わずに唱えてもよい」も一致。
- 切り分け（各8シード）: ラルドだけ差し替え 1.00（L1 で勝つ）／ウォカンナ＋ラルドを差し替え 0.00／ナウ・オア・ネバー＋ラルドを差し替え 0.00。ウォカンナ差し替えの組がシードで 0.38〜0.88 にばらつくのは、配り直した手札に H.D.2. が来るかどうか。オルゼキア（訪れる魔の時刻）・アカシック3 の差し替えは §12 のとおり 0。

**意味**: アカシックの中核は「アカシック3＋訪れる魔の時刻×2」で、勝ち手段（ウォカンナ＋ナウ・オア・ネバー、または H.D.2. 単体）は入れ替えが利く。ウォカンナ・ナウ・オア・ネバーは「1部品」ではなく「代わりのある部品」だった。ランダム組は物差しの緩さではなく、陽性対照の作り方（入口 M が名前で要求する札＝中核、とみなしたこと）の問題。

**直す案（未実装、指揮役の判断待ち）**:
1. 入口局面の中核を「機能の組」で書く。`minimal` に名前の代わりに「どれか1つ」（例: 勝ち手段 = ウォカンナ＋ナウ・オア・ネバー | H.D.2.）を書ける形にし、陽性対照は**代わりの札も含めて組ごと**差し替える。
2. 中核の決め方を実測で確かめる（取り除き試験）: 入口のデッキから部品1種類の全コピーを外して到達率が落ちない札は中核に数えない。今回の切り分けと同じ手順を ruler_control に足せる。
3. 新しいループ L2 は known_combos に「アカシック（H.D.2. 版）」として記録する候補（既知の変種。新規コンボに数えるかは指揮役が決める）。

**合格条件への提案**: 中央値 ≤ 0.05 に加えて、ランダム組の上位（段2 ≥ 0.25 の組）は「要説明」として名前と手順の要約を出し、手順を読んで (a)〜(d) を付けるまで印を「保留」にする。本物のループ（a/b）と分かった組は対照から外して「代わりの部品」として記録し、物差しの不具合（c）・データの誤り（d）なら不合格。最大値を既知の最小と比べる今の警告は残す。

## 14. 中核を「代わりのある組」で書く（2026-11-13、§13 の指揮役決定を実装）

**定義の書き方**: 入口局面 data/loops/entry/<コンボ>.json の `source.core` に、中核の組を並べる。各組は役（role）と代わりの一覧 `any`（どれか1つが揃えばその役が揃う）。

```json
"core": [
  {"role": "エンジン（呪文の無償詠唱）", "any": [{"dm23ex2-009": 1}]},
  {"role": "回収（訪れる魔の時刻）",     "any": [{"dm23bd7-035": 2}]},
  {"role": "勝ち手段", "any": [{"dmrp12-s01": 1, "dm24ex1-038": 1}, {"dmrp07-009": 1}]}
]
```

- `source.core` がない入口（サガ）は従来どおり、minimal が名前で指す札を1札1組（代わりなし）とみなす（loop_entry.core_groups）。
- 揃うの目盛り（assemble）: 組ごとに代わりを1つずつ選んだ全組み合わせ（loop_entry.core_alternatives）の**どれか1つ**が揃えば揃った扱い。素引き確率は包除原理で厳密に出す（any_ceiling）。core_need は1つめの組（表示・互換用）。
- 陽性対照のランダム組（ruler_control.make_randoms）: 組1つを、**代わりの札も含めて組ごと**差し替える（札ごとに別の札へ）。アカシックの勝ち手段なら ナウ・オア・ネバー・ウォカンナ・H.D.2. を全部替える。
- 取り除き試験（removal_cases / judge_removal、tools/ruler_control.py で毎回回す）: 中核の札1種類の全コピーを中核でない札に替え、段2が 0.25 未満に落ちるかを見る。定義上どの代わりにも要る札（required_ids）が落ちない、または代わりのある札が落ちる、なら理由付きで食い違いを出す。定義は自動で書き換えない。
- 要説明: 段2 ≥ 0.25 のランダム組は、data/eval/ruler_control_explain.yaml に説明（a 本物の別ループ / b 中核でない札 / c 物差しの不具合 / d データ・エンジンの誤り）が記録されるまで合格の印を保留する（reason が「保留」で始まる）。a・b は対照から外して記録（summary.explained）、c・d は不合格。§13 の H.D.2. 版（ウォカンナだけ／ナウ・オア・ネバーだけの差し替え）を a で登録済み。
- 既知の別版「アカシック（H.D.2. 版）」: data/loops/entry/akashic_hd2.json（アカシック3場、手札に H.D.2.・訪れる魔の時刻×2、ナウ・オア・ネバーとウォカンナは山札。delta は相手の山札 −2）。陽性対照の KNOWN に入れる。新規コンボには数えない（ユーザー確認中）。
- 候補の札から再録（同名で別ID）を除く: 初回の実行で akashic_hd2 のアカシック3 差し替え先に再録 dm25ex2-cho005 が選ばれ、段2 0.62 の要説明が出た（c 相当、対照の作り方の不具合）。candidates で中核と同名の札を除いて直した。

**実測（2026-11-13、8シード、各組4本）**: 既知 saga 0.12 / akashic 1.00 / akashic_hd2 0.62、ランダム組32組すべて 0.00（中央値 0.00・最大 0.00）、要説明 0 組。判定は不合格（saga と akashic_hd2 が 0.8 未満）。

## 15. FAIR の対局でもループを記録する（2026-11-13、案 F）

`search.game.fair_game` と `play_api.play_turns(record=GameResult)`（assemble が使う）で、FAIR でも `GameResult.loops` を play_game と同じ形で残す。手順・勝敗は変えない（同一シードで main と手順が一致、tests/test_fair_loops.py）。
- 証明書: FairTurnSearch は、採った手に最初に投票した決定化の探索が使ったループ（st.chosen）を `fs.chosen` に残す（`evidence: "determinized"`、何手目か `decision`。同じ形のループは1ターン1回）。決定化した山札の上での計画なので、実際の山札で同じ周回数になったとは限らない。
- パターン: そのターンに証明書が無ければ、実際に指した手順に `pattern_loop.find` をかける（`evidence: "executed"`）。共通の記録関数は `search.game.record_turn_loops`、勝敗の書き込みは `finish_result`（FAIR でも相手の山札切れ勝ちをループ由来なら `loop_deck_out` と書く）。
- ロック: `fair_game(lock_judge=…, lock_rounds=N)`。既定は lock_rounds=0（従来どおり判定しない）。S3 から S4 は import しない。
- assemble.summarize: `effect_win`（勝利効果・山札切れの勝ち）を `effect_loop`（judge の段2が loop）と `effect_other` に分ける。

**実測**（各40局、#408 と同じ条件: seed 0〜39、先後は偶奇、6ターン、budget 200、n_det 8）。手順は #408 と同一なので揃う・勝ちの数字は同じ。増えたのはループの記録:

## 17. リソース型の目盛り（2026-11-13、§6 タスク12 を実装）

道具: `dmsim/eval/resource.py`（`measure_one`・`summarize`）、分布 `tools/resource_dist.py`（結果 data/eval/resource_dist.json）、登録の検証 `dmsim/eval/verify.py` の resource 段。ループ型の段1・段2とは別の欄（登録簿の measured.resource）。
- 入口: data/registry/setups/knight_dmc.json（墓地に DMC、手札に騎士、マナ3=光・水・闇の単色）。手札の残り4枚・盾5枚・山札はデッキ data/decks/knight_dmc.yaml の残りをシードで配る（開始局面は8シードで8種）。自分の1ターン目を探索（budget 200、相手は従来どおり）に指させ、ターン終わりの局面と比べる。
- 数えるもの（重みなしの生の数）: 使ったマナ mana_used（タップした数）、手札から出た札 cards_spent（プレイとチャージ）、手札に入った枚数（Δ手札＋cards_spent）、Δ場、Δ盾。得た量 gain = 手札に入った枚数＋Δ場＋Δ盾、効率 adv = gain /（mana_used＋cards_spent）。
- 注意: チャージも cards_spent に数える（毎ターン1枚なので全組で同じだけ分母が増える）。相手の分は数えない。

**分布**（各8シード。ランダム組は中核1種類を ruler_control.candidates の条件で差し替え、各4組）:
| 組 | adv 中央値（最小〜最大） | gain 中央値 |
|---|---|---|
| 騎士＋DMC（既知） | **1.8**（1.2〜2.4） | 9 |
| 騎士→dmsd07-011 | 0.76（0.71〜1.0） | 4.5 |
| 騎士→dm24-088 / dm23rp3-053 / dmrp15-074 | 0.17 / 0.24 / 0.17 | 1〜1.5 |
| DMC→4組（dm18-053 ほか） | どれも 0.6 | 3 |

既知の最小 1.2 がランダム組の最大 1.0 を上回り、重なりは無い。線を引くなら 1.0〜1.2 の間（例 adv ≥ 1.1）が候補。ただし既知は1件・入口は1種類・相手は抵抗なしの値。**合格線は未定**（指揮役とユーザーが決める）なので、登録簿では resource 段で止めて数字だけ残す。

## 16. 物差しの測定の標準予算を 1500 にする（2026-11-13、指揮役決定）

物差しが測るのは札の組で、探索の速さではない。予算を上げても所要時間はほぼ変わらない（勝てた局は早く終わる）。そこで陽性対照と登録簿の検証の標準予算を 1500 にした。
置き場所は `dmsim/eval/loop_entry.py` の `RULER_BUDGET` と `measure_budget(ls, budget)` で、`ruler_control.run_one` と `loop_entry.measure` はこれを使う。入口局面の `budget` が 1500 より大きければそちらを使う。日次の経路（auto_fix の予算100 など）は変えない。

予算ごとの段2（陽性対照の8シード、案 E #419 入り。所要時間は8局で3〜17秒、予算による差はほぼ無い）:

| 200 | 6/8 | 1/8 | 1/8 |
| 400 | 8/8 | 1/8 | 1/8 |
| 800 | 8/8 | 4/8 | 2/8 |

予算 1500 での陽性対照: saga 1.00、akashic 1.00、akashic_hd2 0.62、ランダム組32組すべて 0.00。akashic_hd2 が基準 0.8 に届かず**不合格**。
