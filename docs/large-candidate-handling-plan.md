# 大きい候補の扱い 実装計画（漏斗方式）

作成: 2026-11-16（検討ドラフト。本文書は計画であり、実装済み機能の説明ではない）
位置づけ: システム完成を最優先とする方針の下位計画。
関連: docs/finisher-auto-identification-plan.md（フィニッシャー自動特定）、
docs/combo-ruler-design.md（物差し）、tools/exhaustive_proto.py（全探索試作とそのログ形式）。

---

## 1. 「大きい候補」の定義

候補1件あたりの状態空間が大きく、全探索では確定判定できない候補の組を指す。

- デッキ構築モードの構成: 固定部品＋残りスロットをプールから選ぶ組み合わせ
  （実測例: 墓地系プール52枚×サガ4部品、slots 2 で 300構成を標本測定）
- 部品の組探索: プールから k 枚の組（3枚組なら C(52,3) = 22,100 通り）
- 40枚デッキ構成そのもの

対義語は「小さい候補」: 配置を固定した局面＋足す1枚（search_setup 型）で、
全探索による確定判定（kill / no-kill の証明）が可能な規模のもの。

## 2. なぜ全探索で直接扱えないか

二重の組み合わせ爆発があるため。

1. 候補の数自体が組み合わせで増える（上記）。
2. 候補1件の中の探索も爆発しうる。全探索試作の実測（2026-11-16）では、
   通常探索が27ノード・0.4秒でキルする局面（saga_setup＋ドラゲリオン）が、
   候補全列挙では数分回しても終わらなかった。原因はノード予算ではなく
   「複数選択の組み合わせ列挙」（墓地15枚からの選択、進化元の選択など）。

したがって「上限を外す」方向では解決しない。大きい候補は段階的に落とす
漏斗（ファネル）で扱い、全探索は漏斗の早い段で「証明つきで捨てる」用途に限定する。

## 3. 原則: 除外と優先付けを分ける

- **除外**してよいのは、証明に基づくフィルタだけ（静的な到達不可能性、
  最小局面での全探索による no-kill 確定）。誤って有望な候補を消さないため。
- ヒューリスティクス（効果分類、過去の成績など）は**優先付け**にだけ使う。
  順序を変えることはあっても、候補集合からは消さない。

## 4. 漏斗の設計

### 段0: 候補の生成と正規化

- 候補は「部品の組の署名」（カードIDの多重集合＋固定条件）で表し、登録簿に
  キャッシュする。同じ署名の再測定をしない（registry の既存運用に乗せる）。
- 機能的に同値なカード（同コスト・同効果タイプ）は等価クラスとしてまとめ、
  代表だけを先に測る。

### 段1: 静的フィルタ（対戦ゼロで落とす）

- ゾーン変換グラフ（zone_graph）で、資源が増える閉路に接続しない部品、
  必要なゾーンへ到達できない部品を除外する。グラフが完全なら到達不可能性は
  証明として扱える。グラフの欠落が疑われる場合は除外ではなく優先度低下に留める。
- デッキ構築制約（文明・コスト帯など形式条件）で構成不可能な組を除外する。
- フィニッシャー分類（finisher 計画の経路A）は優先付けに使う（除外には使わない）。

### 段2: 最小局面での全探索フィルタ（証明つき除外）

- 部品組ごとに最小の入口局面（search_setup 型の固定配置）を作り、全探索する。
- 結果は3値で記録する: kill（部品として成立）/ no-kill（この scope では勝ちなし
  が確定 → 候補から除外）/ unknown（時間内に終わらない等 → 除外せず段3へ送るか保留）。
- 判定の scope（配置・ターン数・シード・設定）は全探索ログの形式
  （ヘッダ＋case_start/case_result、tools/exhaustive_proto.py で試作済み）で残す。
  scope の外に結論を広げない。
- 注意: 最小局面で no-kill でも、他部品との相乗で成立する可能性は残る。
  除外の単位は「部品組＋固定条件」の組であり、単体カードの除外には使わない。

### 段3: 段階測定＋逐次淘汰（サンプリング）

- 段2を通過した候補を、物差しの段ごと（ループ成立→勝利への変換→キル）に測る。
- 局数は一律配分にしない。全候補に少数局（現行の12局規模）を配り、
  成績の上限見込み（信頼区間の上限）が段の閾値を下回った候補から落とし、
  残った候補へ局数を寄せる（逐次半減）。際どい候補の判定がノイズに埋もれる
  現行方式（一律300構成×12局で打ち止め）の弱点を直すのが目的。
- 結果は「勝ちなし（証明済み）」と混同せず、必ず標本数つきで
  「未証明（n局中k回）」として記録する。

### 段4: 登録と回帰

- 段3を通過した候補は発見コンボとして registry に登録し、通常の回帰テストで
  再検証できるようにする（既存の discovered combos の運用に乗せる）。

## 5. 優先順位（何からやるか）

1. **既知ループ×フィニッシャー候補の交差検証**（フィニッシャー計画の経路B）。
   両側とも登録済みの有限集合で候補数が小さく、段2〜段3を飛ばして
   確定判定に近い形で測れる。漏斗の最初の適用先とする。
2. **段2の全探索フィルタ**を combo_search の search_setup 前段に入れる。
   効果は「測る前に証明つきで捨てられる」ことによる測定量の削減。
3. **段3の逐次半減**。現行の一律配分の置き換え。閾値は物差しの校正と合わせて決める。
4. **デッキ構築モード（40枚構成）**は最後。現行のサンプリング測定は当面の
   代用として成立しており、先に直すのは規模ではなく記録形式（3値＋標本数）。

## 6. 実装ステップ

1. 候補署名と等価クラスの定義を combo_search 側に寄せて実装し、再測定を防ぐ。
2. 段1: zone_graph の到達可能性を候補フィルタとして公開する関数を用意する。
   既存の静的閉路列挙の結果を再利用し、新しい解析は作らない。
3. 段2: 全探索試作（exhaustive_proto）の判定部を部品組バッチに拡張し、
   ログ形式をそのまま使う。本実装では TurnSearch 側に統計（到達状態数）を
   公開する拡張が前提（試作の宿題として記録済み）。
4. 段3: measure の呼び出し側に逐次半減の配分ロジックを足す。測定器自体は変えない。
5. 記録: 段ごとの結果を registry / 発見コンボの既存形式に3値＋標本数で書く。
   スキーマは data/schema/ への追加とセット（ログ・スキーマ見直しと連動）。

各ステップは独立にマージ可能で、ステップ2だけでも測定量の削減効果が出る。

## 7. リスクと保留事項

- 段1の静的除外は、ゾーン変換グラフに欠落があると有望候補を誤って消す。
  グラフの完全性に確信が持てない範囲では優先度低下に留める（第3節の原則）。
- 段2の「最小局面」は人手で用意する入口局面に依存する。入口局面の設計が悪いと
  no-kill の結論が実戦の構成に及ばない。scope をログに残し、結論の適用範囲を
  常に明示することで対処する。
- 逐次半減の閾値と初期局数は未校正。物差しの校正（陽性対照・陰性対照）と
  セットで決める。
- 相手の妨害を入れた測定は対象外（現行の「まず1人回し」の方針どおり）。

## 8. 未決事項（ユーザーの判断が要る点）

- 段2で unknown になった候補の扱い: 保留して段3へ送るか、別途時間をかけて
  再挑戦するキューに回すか。
- 段3の初期局数と逐次半減の段数（測定コスト全体の上限感覚）。
