# 探索システムの改善と基盤の実装計画

作成: 2026-11-16（検討ドラフト。本文書は計画であり、実装済み機能の説明ではない）
位置づけ: システム完成を最優先とする方針の下位計画。
関連: docs/exhaustive-search-saga-report.md（全探索試作の実測）、
docs/finisher-auto-identification-plan.md（フィニッシャー自動特定）、
docs/large-candidate-handling-plan.md（漏斗方式）、
docs/approval-rate-20261113.md（カード承認率と上げ方）、docs/performance.md（高速化）。

前提となる実測（2026-11-16、全てこのクローン・Python エンジン）:

- 1ターン内は、抽象状態（骨格＋カウンタ＋残マナ＋ゾーン枚数）での全探索が可能で、
  小規模ケースでは kill / no-kill の確定判定が取れる。
- 複数ターンは「ターン毎に1ターン探索をして最良線を確定する」方式で、
  9デッキ×シード30まで走らせて 3〜4ターンキルを18件発見（うち3ターン7件）、
  全件を再生検証済み。最良デッキ saga_doom_e でキル率 6/30。
- 評価関数 V は判断点ではほぼ平坦（勝ち手と他の手の差が0〜6点）で、
  順序付けに使うとノード数・時間とも悪化する（同ケース比較:
  saga_doom seed16 で rank 48kノード／value 129kノード）。

## 第1部 探索システムのさらなる改善点

### 1. ターン横断の探索（最重要の未解決）

現状の複数ターン方式は、ターン毎に最良線を確定して進むため、
「そのターンでは評価が低いが、次ターンのキルにつながる準備」を挟む線を見逃しうる。
このため現在は「キル率が低いのがデッキの限界なのか、探索の見逃しなのか」を
切り分けられない。キルの有無の解釈ができない状態が一番の問題。

改善の順序:

- (a) **見逃し率の物差しを先に作る**。小規模構成（短縮デッキ、部品固定の局面）で
  ターン境界でも分岐を保持する完全な横断探索を実装し、現在の貪欲方式と突合して
  見逃し率を実測する。物差しなしに (b)(c) の効果は測れない。
- (b) ビーム的横断: 各ターンの上位 k 線を保持して次ターンへ渡す。
- (c) 目標指向: loop_first の2段分離（ループ成立→勝ちへの変換）をターン軸へ拡張し、
  「ターン T でループ成立」を中間目標として逆向きに誘導する。

### 2. 順序と評価の分離（実測結論の実装化）

- V は葉評価に専念させる。判断点の順序付けには使わない（実測で否定済み）。
- **順序専用の軽い指標**を新設する: ループ証明書に到達したか、ストック量、
  フィニッシャーのゾーン到達、zone_graph 上の目標までの距離など、
  物差し（combo-ruler）の段を数値化したもの。
- **統計順序**: 探索ログと explog から、部品・カード単位の勝率とコンボ貢献を
  集計する。効かせる場所は判断点の微細な順序ではなく、候補（デッキ・部品）
  レベルの優先付け（漏斗方式の段3と接続）。
- 本体の `_rank`（手作りヒューリスティクス順序）は即時廃止ではなく、
  順序戦略として差し替え可能な形に分離し、greedy_policy との共有を切る。
  既定戦略の切り替えは統計順序の実測後に判断する。

### 3. 主張範囲の拡大: 相手モデル

現状のキル検証は無抵抗相手（マナチャージのみ）。シールドトリガーや防御札が
ある条件での生存率は未検証。トリガー/防御入りの相手デッキでの検証セットを作り、
「無抵抗で見つけたキルがどれだけ残るか」を測る。infoset の決定化サンプリングとの
接続はその後。

### 4. ドローの確率評価

現状は固定シード列挙で「n シード中 k 回」。STATUS の定義する強いコンボ
（高確率で3〜4ターン）に答えるには、キル率を推定値＋信頼区間として記録し、
必要なシード数を目標精度から逆算できる形にする。逐次半減（漏斗の段3）と接続する。

### 5. 速度

実測では重いケースが1件100〜440秒、30シード×9デッキの逐次走行で約50分かかった。

- スキャンの並列化: シード×デッキは独立。プロセス並列でほぼ線形に短縮できる。
- Rust コアの検証と適用（第2部フェーズ2と連動）。
- docs/performance.md の既存候補（chars のターン内キャッシュ等）の実施。

### 6. 発見パイプラインへの接続（既存計画の実装順）

フィニッシャー自動特定（計画書あり）→ 漏斗方式の段2フィルタを部品固定探索へ
接続 → 走行が増えるほど統計順序の材料が貯まる、という順で既存計画を実装に落とす。

## 第2部 基盤の実装計画

### フェーズ0: ログとスキーマ（小さく、後の全測定の土台）

- 未作成のスキーマ3件を `data/schema/` に追加し、`tests/test_file_schemas.py` の
  レジストリに登録、実物ログで検証する:
  1. explog（`dmsim/eval/explog.py` の版つき JSONL）
  2. 分析ログ: 生ログと要約の間の中間層。turning_point 行
     （game 参照、turn、局面 digest、chosen、best、value_chosen、value_best、loss）
  3. combohunt 結果
- 全探索ログスキーマ（作成済み）に、multiturn ヘッダの項目（order、stages）を反映する。
- 3層分離の置き場を確定する: 生ログ（既存 logs/explog）、分析ログ
  （logs/analysis/<experiment_id>/）、要約（experiment 単位の集計 JSON）。
- 原則: **設定の完全記録**。2026-11-16 のシード拡大走行で、ヘッダに順序方式が
  無く「どの順序で測ったか」をファイル更新時刻から復元する羽目になった。
  再現に必要な設定は全てヘッダに含める（当該欠陥は修正済み）。

### フェーズ1: カード基盤の回復（承認の詰まり解消）

現状は docs/approval-rate-20261113.md の集計が正確で、要点は:

- 詰まりは「自動承認が止まっている」「未変換 10,521枚」「語彙不足 2,899件」の3つ。
  **人の確認待ちで止まっている札は実質ゼロ**。
- 自動承認（auto_approve、Actions で6時間ごと）は無料枠切れで 2026-11-10 から停止。
  台帳（cards-data ブランチ）の承認 1,613件は、語彙・定義の変更で stale になり
  未再検査。手元での試行では40/40が再承認（1枚約1秒）。

手順:

1. auto_approve をローカル/ワーカーで再実行し、stale 分を再承認する
   （1,600枚前後、所要30分程度の見込み）。Actions 枠に依存しない定常運用に変える。
2. 台帳を main 側からも読める形にする（集計スクリプトは対応済み）。
3. 台帳未投入の変換済み 8,075件を投入し、LLM 変換分の effect: ok 通過率を測る。
4. stale の粒度を細かくする: 語彙変更時に、変更された op を実際に使う札だけが
   stale になるよう依存追跡を入れる（大量一括 stale の再発防止）。

段階つき承認（同ドキュメントの案B）と「使う札から優先」（案C）は、
同ドキュメント側の判断待ち事項として残す。

なお、このクローン（main のみ）で実効的に使えるのは real.yaml の60枚級であり、
フェーズ1の完了で実効プールが1,600枚級に戻ることが、環境としての最大の前進になる。

### フェーズ2: Rust コアの検証

- 実行環境（CI/ワーカー）で dmcore をビルド可能にし、同一シードの digest 一致を
  回帰基準として通す（`play.replay` の仕組みが既にある）。
- 速度ベンチ: 代表ケース（saga_doom seed16、Python で rank 48kノード・129秒）で
  Python 比を実測し、大規模スキャンへ適用するか判断する。
- 不一致が出た場合の切り分け手順（digest 差分の最小再現）を文書化する。

### フェーズ3: 実験管理の定型化

2026-11-16〜17 の改善開発で手作業として繰り返し発生した試行錯誤・検証の棚卸し
（自動化候補の一覧）。優先順は「毎回発生し、ミスの実害が出たもの」から。
1〜6 と 8 は 2026-11-17 に実装済み（各項目にツール名を併記）。

検証系:

1. **記録の再生検証の1コマンド化**（最優先）【実装済み: tools/verify_records.py】:
   キルが出るたびに使い捨てスクリプトで digest 照合をしていた（5回以上）。
   記録の glob → 全件 strict 再生 → 合否一覧。既存の記録41件は全件 OK を確認。
2. **ゴールデンケースの回帰ランナー**【実装済み: tools/run_golden.py +
   tools/golden_cases.yaml】: ツール改修のたびに代表ケース（ケースD の段1キル、
   ケースB/C の勝ちなし証明、hidden beam4 の2ターンキル保持など）を手で
   再走していた。期待判定つきケース集（6件）を1コマンドで回し、判定の変化を
   検出する。全ケース PASS・ノード数も実測と一致（約2分）。

実験系:

3. **スキャン集計の tools 化**（最優先）【実装済み: tools/scan_report.py】:
   デッキ×シードのキル率表、3値（kill / no-kill証明 / unknown）の内訳、
   Wilson 95% 信頼区間までを自動生成する。今回の集計は手作業スクリプトで
   行い、順序方式の混在データの誤説明という実害も出た。既知の集計
   （第1バッチ＋scan2 で18件・3T×7、scan3 の saga 段2で2件）と一致を確認。
4. **比較実験のグリッドランナー**【実装済み: tools/exp_grid.py +
   tools/grid_example.yaml】: 順序×段×beam 幅などの比較を、その都度シェルの
   直列実行で組んでいた。run の一覧（label・tool・args）を YAML で指定すると
   走行と比較表まで出す。
5. **記録ファイルの上書き防止**【実装済み】: crossturn の記録名が設定
   （trim-order 等）を区別せず、後の走行が前の証拠を上書きした（3回発生）。
   記録名に設定の sha256 先頭8文字（cfg_suffix、proto/multiturn/crossturn 共通）
   を入れるよう改修。同じ設定の再走行は決定的に同じ名前になる。
6. **設定の完全記録の lint**【実装済み: tools/check_log_headers.py】:
   ログヘッダに order が無く、データの出所をファイル更新時刻から復元する
   羽目になった。全実験ログのヘッダ必須項目（order・段・trim・鎖ファイル等）を
   点検する。現行ログ46件では修正前の24件（旧スキャンの order/stages 欠落、
   初期 frontier ログの trim_order 欠落）を検出した。実験 ID（設定の sha256、
   explog で採用済み）の全探索系ログへの統一は未実施で残る。

今後発生するもの:

7. **相手モデル×キル記録の検証マトリクス**【未実装】: 相手モデル検証
   （探索3）を始めると、キル記録×相手方策の組み合わせ検証が定例化する。
   相手モデルの実装が前提。
8. **パラメータ感度スイープ**【グリッド定義で表現可能】: beam 幅・frontier
