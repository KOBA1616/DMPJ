# ループと手順の自律発見（設計と v1 の結果）

AIが、独自のループを発見し、初期盤面からループ導入とループキルまでの手順を見つけ、
その手順を再利用できる台本（方策）として抽出するための設計と実験結果。
実装は `tools/discover_pipeline.py`。

## 学習の2層分離

プレイの判断は、粒度の違う2層に分けて学習する。混ぜると、学習対象も評価軸も曖昧になるため。

### マクロ（大局観）― ターンの狙い

ターン（あるいは局面）の単位で「このターンは何をするか」を決める層。

- 狙い（intent）の例：見切り発車してでも攻める／手札とマナを整える／リーサル（ループキル）を
  狙う／相手を妨害する（ロック・資源を削る）
- 入力は局面全体の特徴：ターン数、手札・マナ・山札の枚数、目標ループの部品が
  どのゾーンにあるか、相手のシールドと山札
- 出力は狙いと、それに伴う探索の動かし方（予算、ストック方針、目標部品）
- 学習対象は「特徴 → 狙い」の対応。評価軸は狙いごとの到達率・勝率
- 実装：`MacroPlanner`（v1 はサガループ目標の規則ベース。setup / enter_loop / execute を切り替える。
  disrupt は相手モデルが簡易なため将来の拡張）

### ミクロ（詳細）― ターン内の決定

個々の決定をどう答えるかの層。

- 対象：カードのプレイ順、ループの手順（捨てる札・蘇生先・対象の選択）、
  唱える／出してよいか否か、リソース（マナ・山札・キーパーツ）の温存
- 入力は決定の種類と文脈、出力は選ぶキー（候補の順序付け）
- 学習対象は「決定の種類と文脈 → 選ぶキー」の選好。評価軸は探索ノード数と勝率
- 実装：`MicroPolicy`（v1 は決定の種類ごとのキー選好率。文脈条件付きが次の拡張）

大まかには、マクロが「どの山を登るか」を決め、ミクロが「足の置き方」を決める。
探索（TurnSearch）は両層に挟まれ、マクロの狙いの下でミクロの案内を受けて手順を探す。

## パイプライン

1. ゾーン変換グラフでループ候補を静的に列挙する（`zone_graph.find_cycles`）
2. 初期盤面から探索の収集モードでループ証明書を動的に発見し、再生で検証する
   （`loop_first.discover_loops`）
3. 教師（最初は既存の台本）で案内した探索の勝ち手順を、最初から再生しながら
   決定データ（種類・選択肢・選んだキー）を収穫する
4. 収穫データからミクロ選好を学習し、方策ファイル（JSON）に出す
5. 学習方策だけで案内した探索を、未使用シードの初期盤面で検証する
6. マクロが狙いを切り替える階層版でも検証し、ミクロ単独と比較する

## v1 の結果（サガループ中心、2026-10-26）

条件：手札サガ・コダマ・イザナギ等、墓地タイフーン・サガ、山札18枚に
ドラゲリオン／イワシン／シャコガイルを乱数位置へ挿入した初期盤面。
勝ち＝そのターンのうちの勝利。探索予算は TurnSearch 3000。

| 段階・方式 | 結果 |
|---|---|
| 候補列挙 | 869件（max_cards=2） |
| 動的発見 | 初期盤面5件から相異なるループ5種、うち3種が再生検証済み |
| 手順の収穫 | 訓練盤面20件で13勝、決定レコード790件 |
| 案内なし探索 | 0/20勝（平均2,214ノード） |
| 台本単体 | 11/20勝 |
| 台本で案内した探索 | 13/20勝（平均397ノード）、未使用シードでは15/30勝 |
| 学習方策（ミクロ）で案内した探索 | 未使用シードで15/30勝（平均604ノード）。人の台本と同等 |
| マクロ＋ミクロの階層版 | 未使用シードで15/30勝（平均604ノード）。この盤面群ではマクロの狙いが全件 enter_loop になり、ミクロ単独と一致した。狙いの差が出るのは、部品の揃い具合が混ざった盤面群で測る必要がある |

学習済み方策の例は `tools/loop_policy_saga.json`（段階4の出力）。

## 次の段階

- 候補列挙の869件から初期盤面を自動生成し、未検証の候補を動的に確かめる（独自ループの探索）
- ミクロ選好を文脈条件付きにする（山札枚数・部品の位置で選好を変える）
- マクロの狙い選択自体の学習（狙いごとの到達率を報酬にする）
- expert iteration：学習方策が集めた勝ち手順を教師に足して再学習する
- 妨害（disrupt）の本格化は、相手モデルの拡張が前提

## 大局観 v2（段階目標の鎖から Plan を出す）— 2026-11-10
- `dmsim/plan/macro.py` の `MacroPlanner(stages)`: 満たされている最後の段の次を狙いにし、`Plan`(dmsim/eval/vfeatures.py と共通)を返す。intent は setup/chain/execute/done、budget は残り段数に比例。自分の見える情報だけを使う。
- V への接続: `v_priority(..., plan=, plan_w=)`。計画項 = 達成段数 + 現在の段の充足率 + 0.5×次の段の充足率。`plan_w` 既定 0（採用前）。
- 測定: `python tools/eval_macro.py --stages data/eval/stages/tenmon.yaml --deck data/decks/tenmon.yaml`（強制3枚・14ターン・幅150）。
  天門の到達段数(8seed平均 /10): plan_w=0 → 2.62、30 → 2.62（同一）。1500 も先頭4seedで基準と同一(3,2,3,3)。**改善なし → 既定は不採用(0)**。
- 所見: 段階ごとの到達探索が段4(ミルザム着地)で止まる。計画項は段を進める情報を足せていない。次は逆算側(手順3)の中継点の細分化。
- 大局観 v2.1(2026-11-10): `macro_prio(stages, plan_w)`。局面ごとに MacroPlanner が現在の段を決め直して V の計画項に使うので、段をまたぐ reach_chain でも1つの prio で足りる。
  測定(vgate.chain_score と同じ force_hand 開始・天門・幅150・14ターン・8seed、合計到達段数、under_w=res_w=0): 基準20(3,2,3,3,3,2,2,2) → plan_w=300/1500/5000 いずれも24(全seedで3段)。vgate の採否基準(基準を上回る)を満たす。ただし差は「段2(エメラルーダ着地)を安定させる」分で、段4以降は未突破(別スレッドの shield_under 調査待ち)。plan_w の既定採用は日次ゲートで確認してから。
- 段階目標の自動生成(2026-11-10): `tools/gen_stages.py <combo>`（dmsim/plan/stagegen.py）が LoopSpec の最小盤面 M か combos.yaml の leaf_parts から、ゾーン順(手札→場→墓地→盾→マナ)に累積する鎖を作る（山札・相手側の述語は捨てる）。サガで生成した6段を vgate に通すと、4seed で base 7 → plan_w=1500 が 12 で採用（従来の重み候補は同点7）。生成物は data/eval/stages/<combo>.generated.yaml（手書きの <combo>.yaml とは別）。
- **訂正(2026-11-10・12seed の再測定)**: 上の「天門 7→8」「サガ 7→12」は 4seed の小標本で、その後 main に入った探索の修正(keep_later・重複除外など)の前の値。天門を 12seed(同じゲート条件)で測り直すと base 32、under/res の重み候補 32・32・31・31、`plan_w=1500` の2候補は **27(下回り)** で採用なし。plan_w は現状「効く」とは言えない。既定は 0 のまま(vweights に plan_w は入らない)。採否は日次ゲートで積み増して判断する。
- ゲートの不具合修正: 強制開始の札が山札に無い seed(盾に落ちた等)があると、全体が `n=0` になっていた。その seed だけ飛ばす(全候補で同じ seed が飛ぶ)。
- サガの12seed再測定(2026-11-10、強制開始できない1seedを除く n=11、自動生成の6段): base 29、under/res の重み候補は全て29(同点)、`plan_w=1500` の2候補は 32 で採用基準を満たす(+3、差は小さい)。天門は同条件で下回り(base 32 に対し 27)なので、計画項の効果はコンボ依存。既定は 0 のまま、日次で積み増して判断する。
- **plan_w の大きさ(2026-11-10・12seed の掃引、合計到達段数)**: 天門 base 32 / plan_w=30→**43** / 100→37 / 300→39 / 1500→27。サガ base 29 / 30→33 / 100→34 / 300→36 / 1500→32。1500 は計画項が現在の段の目標(GOAL_W=1000)と同じ桁になり、次の段の部分点を狙って今の段を終えにくくしていた(基準が先へ進んだ seed で段2に止まる)。計画項は同順位の振り分け程度(数十〜数百)が適正。ゲートの候補を 1500 から 30・100・300 へ差し替え。両コンボで基準を上回るのは 30 と 300(合計76・75)。
- 勝ち探索への適用(2026-11-10): `bestfirst.beam(prio=)` で順位づけを差し替えられるようにし、天門(force_hand開始・14ターン)で `macro_prio` を勝ちの発見で測った。幅150: 全条件 0/8(基準・plan_w=30・300 とも)。幅1000(4seed・約9分): 基準 1/4、plan_w=30 は 0/4。標本が小さく、**計画項が勝ちの発見を増やす証拠はまだ無い**(段階到達は増えるが、勝ち(盾10枚+アレフティナ)まで届かない)。次は最後の段(盾8→10→勝ち)で止まる理由を調べる。
- **plan_w の最終比較(2026-11-10・main に #340/#343 等が入った後・12局・`tools/eval_plan_chain.py`、生データ data/eval/plan_chain_20261110.jsonl)**: 合計到達段数(強制開始できない局を除く。天門12局・サガ11局):

  | | 計画なし | 30 | 100 | 300 |
  |---|---|---|---|---|
  | 天門 | **47** | 43 | 37 | 39 |
  | サガ | 30 | 33 | 34 | **36** |
  | 合計 | **77** | 76 | 71 | 75 |

  段別に届いた局数(天門、計画なし): [12,12,10,10,3,0…]、300: [12,10,8,8,1,0…]。サガ、計画なし: [11,11,6,1,1]、300: [11,11,8,3,3]。届いた通しターンの中央値は、天門の段2〜4が計画なし 11→13、100/300 は 11 のまま(早い)、サガは同等(13前後)。
  結論: 探索側の修正(#340 等)で計画なしの天門が 32→47 へ上がり、計画項の優位は消えた。サガだけは計画項が効く(300 で 30→36)。**全体で最良の値は「計画なし(0)」で、既定は 0 のまま**。コンボ別の採否は日次ゲート(`vweights.yaml`)に任せる。ドリル＋ジョバンニは検証専用のため測っていない。
- **天門で計画項が逆効果だった原因と修正(2026-11-10)**: 落ちた局(seed 6/10/11/12)で計画項を1つずつ外して調べた。(1) 段の番号を「満たされた最後の段の次」で決める作りだと、手前の段の盤面を崩したとき番号が下がって減点になり、段を進められない(seed 6/10: 4→1)。(2) 次の段の充足率の先読み(0.5)は、今の段を終える前に次の段へ寄る(seed 12)。「最初の未達の段を狙う・先読み0」に直すと、落ちた4局は基準と同じ 18(元の計画項は 10)。
  直した後の12局(天門12・サガ11): 天門 plan_w=30/300 とも 47(計画なしと同じ=逆効果は消えた、利得もなし)、サガ 30→30 / 300→**33**(基準30。直す前の 36 より小さいが基準超え)。vweights.yaml にはサガの plan_w=300 だけを入れた。計画の項が reach_chain の中で効くのは「段目標が探索の目標と二重になる」ため限定的(reach_target が現在の段の充足率を既に加点している)。

### 小さい plan_w の測り直し（2026-11-10、12局）
tenmon: base 47 → plan_w 1 / 3 とも 47（中立）。saga: base 30 → plan_w 1 / 3 とも 30（中立）。plan_w=300 のみ saga 33。小さい値は害も益もない。

### plan_w の追加測定と vweights の見直し（2026-11-10）
- 天門 plan_w 10 / 30（12局）: ともに 47。計画なし(47)と同じで、中立から上がる値は見つからなかった。
- サガ plan_w=300 の増局: 実行環境が約10分ごとに再起動され、測定が途中で消えるため 2局ずつ区切って回した。24局には届かず、計画なし 13局=35 / plan_w=300 11局=33（生データ data/eval/plan_chain_20261110_chunks.jsonl）。12局時点の「30→33」の差は増局で消えた。
- V gate スレッドの条件（幅40・seed 1..10・under_w=res_w=0）では 計画なし23 / plan_w=300 は21 で、わずかに劣った。
- 結論: 絶対値 plan_w=300 は有意な上積みなし。vweights.yaml は main 側で V gate の正規化版（plan_w=-0.1）に置き換わったので、そちらに任せる（本記録は旧方式の測定）。
- アカシック: 段階目標の元データ（leaf_parts / loopspec）が無く仮説扱いのため、推測で段階目標を作らず、計画項の測定は見送り。検証済みの最小盤面ができたら gen_stages で同じ手順を回す。
