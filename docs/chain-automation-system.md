# 鎖自動化システム: 段階目標の鎖の生成・検証・運用

作成: 2026-11-18
位置づけ: 大局観（MacroPlanner）の段階目標の鎖を、手書きでなく自動で
用意し、検証を通してから保持判断に使うための仕組みの全体像。
設計の検討経緯は docs/phase-chain-plan.md、実測は
docs/exhaustive-search-saga-report.md §5.9・§5.10 と phase-chain-plan §7.5。

---

## 1. 目的

ターン横断探索の保持判断（どのターン終了局面を次ターンへ残すか）は、
確定した責務分担では大局観の領分であり、局面の良し悪しは「段階目標の
鎖への充足率」で測る。ところが鎖をコンボごとに手書きしていては、
コンボが増えるほど破綻する。また、手で調整した順序関数（辞書式の
特徴量順序）を保持の標準にすると、調整したケースへの過適合
（ガラパゴス化）を招く。鎖はコンボ自身の検証済み手順から生成される
ため、コンボが変われば鎖も変わる — これが汎化の経路になる。

方針（2026-11-18）: 順序関数の既定化は汎化が済むまで見送り、
保持判断は本システム（大局観の鎖）によって進める。

## 2. 全体像

```
検証済み記録 ──→ 抽出 ──→ 鎖の元データ ──→ コンパイル ──→ 鎖 (stages)
(make_record)   (登録側)                  (stagegen)        │
                                                            ↓
                              ゲート（診断＋保持テスト）─ 不採用なら戻す
                                                            │
        消費: MacroPlanner が現在の段と充足率を出す ←────────┘
              ├─ crossturn の plan trim（保持判断）
              └─ 評価関数 V の計画項（stage_fraction）
```

原則:

- **新しい部品は作らない**。抽出・コンパイル・保管・消費・検証は
  既存の責務の延長に置く（phase-chain-plan §3）。
- **消費側（MacroPlanner）は変更しない**。Plan の形はどの出し手でも
  同じ形、が設計原則。
- **生成と採否を分ける**。ゲートを通らない鎖は標準に混ぜない
  （V の重みに対する vgate と同じ構図）。
- **公平性**: 鎖は自分側の見える情報だけから作る。山札の中身
  （名前つき deck 述語）と相手側の述語は捨てる。自分の山札の
  残り枚数（"*" の枚数）は公開情報として使える。

## 3. 構成要素

| 要素 | 場所 | 役割 | 状態 |
|---|---|---|---|
| 入力 | `logs/exhaustive_records/` 等 | 検証済み手順の記録（make_record 形式）。再生で digest が一致するものだけを使う | 運用中 |
| 抽出器 | `tools/chain_extract.py` | 記録を再生し、自分のターン開始局面のスナップショットから勝ち軌跡の共通通過点を段として抽出する | 実装済み（試作、サガで検証） |
| 登録側 | `dmsim/plan/combo_sequence.py` | combo_hunt の検証済み結果を計画として登録簿へ。現状は「部品が手札にそろう」1段のみで、軌跡由来の段は後続の仕事として docstring に明記 | 部分実装 |
| コンパイラ | `dmsim/plan/stagegen.py`、`tools/gen_stages.py` | 部品データ（LoopSpec の最小盤面／combos.yaml の leaf_parts）から累積の鎖を生成する。生成物は「手で直さず、元データを直して作り直す」 | 実装済み（静的入力のみ） |
| 保管 | `data/eval/stages/*.yaml`、registry（PlanSpec.params["stages"]） | 生成は `<combo>.generated.yaml`、手書きは `<combo>.yaml`（上書きしない） | 運用中（正本の所在は未決、§6） |
| 消費 | `dmsim/plan/macro.py`（MacroPlanner） | 局面と鎖から「最初の未達の段」と充足率（stage_fraction）を出す | 実装済み（変更しない） |
| 保持への接続 | `tools/exhaustive_crossturn.py` の `_trim_score(plan)` | スコアは (stage_fraction,) ＋順序関数 v2 の同点解消。保持判断の主軸は充足率 | 実装済み |
| ゲート | `tools/chain_gate.py` | 候補の鎖の採否を2測定で判定する（§5） | 実装済み |
| 参照実装 | `tools/saga_loop_stages.yaml` | 手書きの実行フェーズの鎖。抽出・生成の比較対象 | 実験用 |

## 4. 鎖の形式

`stages` の列。各段は `name` と `target`（ゾーン → {カードID or "*": 枚数}）
を持ち、前の段の条件を含む累積形にする（MacroPlanner は最初の未達の段を
狙うため、累積でないと充足率が崩れる）。

```yaml
stages:
- name: hand:dm22ex1-007x1
  target:
    hand:
      dm22ex1-007: 1
- name: graveyard:dm22ex2-021x1
  target:
    hand:
      dm22ex1-007: 1
    graveyard:
      dm22ex2-021: 1
```

静的な最終盤面（部品の所在）は stagegen が作れる。一方、実行フェーズの
進みは軌跡の性質（墓地が 12→16→21 枚と育つ等）であり、静的入力には
表現する場所がない — 抽出器が担うのはこの部分で、枚数の閾値は
「キルまでの残りターンごとに、勝ち軌跡が確実に通過する水準」から取る。

## 5. ゲート（採否の検証）

候補の鎖について2つの測定を行い、両方を通れば採用する:

1. **診断**: 代表シナリオ（hidden seed1）のターン1終了局面に充足率を
   付け、最速キル局面の充足率順位が beam 幅（4）以内に入るか。
2. **保持テスト**: beam4＋plan trim の横断探索で、hidden seed1〜4 と
   prep seed1〜3 の最速キル（2ターン）を保持できるか。ノード数は
   基準（順序関数 v2 の実測）を大きく超えないか。

実測（2026-11-17、phase-chain-plan §7.5）:

- 抽出チェーン（記録11件から自動生成、3段）: **PASS**。診断順位は
  1・3・8位で手書き版（0・1・2位）より弱いが、保持テストは全シードで
  2ターンキルを保持しノード数も基準と同等だった。保持に必要なのは
  診断順位の完全な一致ではなく「beam 幅の中に最速キル局面が残ること」。
- 生成チェーン（部品集めのみ）: **FAIL**（hidden で3ターンキルに劣化）。
  既知の判定をゲートが再現したことで、ゲート自体の妥当性も確認できた。

## 6. 汎化の課題と判定基準

汎化の判定基準: **サガ以外でも、鎖による保持が frontier の結果
（キルターン）を beam のコストで再現できること**。

残作業（phase-chain-plan §7 の段3以降）:

1. **stagegen への軌跡入力の追加**: 実行フェーズの鎖を抽出器の試作から
   生成パイプライン（gen_stages.py）へ昇格させ、実行フェーズ込みの
   .generated を出せるようにする。あわせて combo_sequence の stages を
   登録時に軌跡由来の段を含む形へ拡張する。
2. **抽出の改善**: 診断順位の弱さの改善（ターン終了局面もスナップ
   ショットに含める等）。ドラゲリオンの手札条件が抽出に入らなかった
   件（キルターン開始時点で未所持の記録があるため）もここで扱う。
3. **サガ以外での通し確認**: 天門など鎖と記録が既にあるコンボで
   生成→ゲート→保持テストを通す。
4. **デッキケースへの適用**: 0ターン目開始のデッキケース（doom_e
   seed24 のターン2候補374件等）で、plan trim が正解局面を上位に
   置けるかを測る。デッキ毎の鎖生成を探索の実行経路に組み込む。
5. **フェーズごとの鎖の選択**: 部品集め／実行／仕上げで鎖を分け、
   大局観が局面に応じて鎖を選ぶ（形式は変えない）。

未決事項:

- 共通ガード（生存: 次のドローで負けない等）を段として差し込むか、
  充足率の計算から分離するか。段は「満たし続ける条件」であり、
  累積の単調性と衝突しうる。
- 枚数閾値の決め方（残りターンごとの最小値か分位か）と、記録が
  何件未満なら実行フェーズの段を作らないか。
- 鎖の正本を registry（PlanSpec）と data/eval/stages のどちらに
  置くか（現状は両方が存在する）。段3の前提として一方向の生成関係に
  整理する。
