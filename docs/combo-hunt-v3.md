実装: `dmsim/discovery/hunt3.py`、実行: `tools/combo_hunt3.py`、テスト: `tests/test_hunt3.py`。
土台は v2（`dmsim/discovery/hunt2.py`。v2 の記録は hunt2 のモジュール冒頭と
`tools/combo_hunt2.py` の冒頭、および Kaggle 実行の記録 `~/workspace/kaggle_verify2/README.md`）。

## ユーザーの定義（2026-11-25 明確化。これが仕様）

- ループ（エンジン）とは、最小盤面 M を維持したまま、そのターン中に、効果と能力の連鎖によって
  アドバンテージが増加する構造。発見は「ループの最小パーツ（エンジン）」と
  「得たリソースから勝利するコンボ（変換）」に分ける。
- エンジンの同一性は増分ベクトルで見る。出力リソースが変われば別エンジンとして扱う
  （実例: サガ単独は {山札−1, 墓地＋1}、サガ＋《死神覇王 XENARCH》は {山札−1, 手札＋1} で、
  後者は手札を単調増加させるループとして機能している）。
- 変換は、資源を恣意的に莫大化した試算ではなく、明示的なループによって実際に増加するリソース、
  効果ストック、無限回使用できる効果・能力を利用するもの。増えたリソースの種類に応じて変換を探す
  （例: 手札を増やすエンジンには、手札を消費・枚数で勝つ変換を当てる）。

## v2 の不備と v3 の差分

| # | v2 の不備 | v3 の対処 |
|---|---|---|
| 1 | 組を一括で判定し、最小性・必要性の検証がないため、寄与ゼロの相方（乗客）が合格した（合格17組中16組がサガ単独と同一増分） | `judge_engine3`: 組全体の合格後、増分ベクトルを「エンジンの同一性」として固定し、「抜く／枚数を減らす」縮小を同一性が保たれる限り繰り返し採用する（貪欲な最小化）。残った最小コアの各カードは、縮小すると同一性が保てないことを確認して必要性を記録する。同一性が変わる縮小（例: XENARCH を抜くと増分が墓地型に戻る）は採用しない＝別エンジンとして扱う |
| 2 | 変換判定が「増えた資源」を身代わり札で人工的に最大化した局面から始まっていた（`judge_conversion` の extra 注入: 墓地＋身代わり10枚、手札＋身代わり4枚、マナ10枚、山札を薄く） | `judge_conversion3`: 認定済みエンジン（最小コア＋変換札1枚）を実際に回す段1（資源評価の探索）で到達した実局面をそのまま引き継ぎ、段2（勝ち狙いの探索）で勝ちを探す。資源の注入はしない。引き継ぎ時点の局面要約（各ゾーン枚数・手札の中身）と、段1で実行された周回を結果に記録する |
| 3 | 変換候補が特殊勝利カタログ固定で、エンジンの出力リソースに連動していなかった | `pair_conversions3`: 候補カードが「使うゾーン」（束の移動元・前提ゾーン・効果が参照するゾーン）を静的にタグ付けし（`conversion_catalog3`）、エンジンの増分ベクトルから決まる型（墓地型／手札型／マナ型／盤面型／山札切れ型／圧力型）と重なる候補を優先する。少なくとも手札型と墓地型は区別される（テストで担保） |

同一ターン性について: 現行の検出（`dmsim/search/game.py` の `record_turn_loops`）は
1ターン分のログ区間（ターン開始時の局面→ターン終了時）ごとに回帰を測るため、記録される周回の
増分は同一ターン内に閉じる。v3 はこれを合格条件として明示し、結果に `within_turn` と
`own_turns`（周回が使われた自分のターン番号）を含める。

解釈上の判断（明示）:
- 最小性は「同一の増分ベクトルが保たれるか」で判定する。抜くと増分が変わるカードは、
  そのエンジンについては必要とみなす（ユーザーの「同一性は増分で見る」に従う）。
- 変換判定で変換札は開始時に1枚だけ手札（特殊勝利クリーチャーは場）に置く。
  これは「変換札を引けている」ことの仮定であり、資源の注入ではない（v2 でも同じ置き方）。
  エンジンの出力リソースそのものは段1の実プレイでのみ増える。
- 段1のターン数（既定2）と周回数は探索の実行に依存する。ただし周回数には増分ベクトルから
  決まる上限（lap_cap、既定12周）が付き、決着前に止めて引き継ぐ（「残課題の解消」参照）。
  「無限回使用できる効果・能力」は、段1で実際に周回が実行され、その到達局面に
  効果ストックや再利用可能な状態が残る形で引き継がれる。

## 残課題の解消（2026-11-25、成果物は ~/workspace/combo3/xenarch3_fixed.json と controls3_fixed.json）

### 修正1: 蓄積段の停止条件（`judge_conversion3` の `delta` / `lap_cap` 引数、`_play_accum`）

仕様（エンジンの増分ベクトルから決まる汎用形。エンジンごとの手書き条件はない）:

- 蓄積量は周回数で数える。開始局面と現在局面の差分 ÷ 増分ベクトルで推定周回数を出し
  （`_laps_estimate`）、上限 `lap_cap`（既定12周）に達したら止める。
- 減るゾーンが「あと2周分」まで減ったら、周回上限より先に止める（枯渇による決着の回避）。
- 結果には「何周で・何ターンで・なぜ止めたか（stop_reason）・切り取りの有無」を記録する
  （各行の `accum`）。

実装上の要点（素直な方法が2つとも失敗したため、この形になった）:

- ターンは探索（play_game＋TurnSearch）に任せる。ただし葉評価は蓄積専用のもの
  （`_accum_value_fn`）に差し替える: 終局した局面は資源量でなく勝敗で評価し（負け＝最低値）、
  増えるゾーンは「開始枚数＋増分×lap_cap」で頭打ちにし、超過周回には減点を付ける。
- それでも行き過ぎたターン（負けで決着／周回上限の超過。ただし勝ちで決着したターンは除く）は、
  そのターンの決定記録（`eng.log`）を開始局面から再生し、停止条件が発火した決定の直後で
  切り取った局面を引き継ぎに使う（`_replay_until`）。再生した局面は実際に選ばれたラインの
  途中経過そのものなので、到達可能性は保たれる。
- 失敗した素直な方法: (1) ターン単位で止める＋価値関数の上限だけでは止まらない。
  探索予算を使い切った残りは貪欲ロールアウトが受け持ち、そちらは価値関数を見ないため
  ループを手で回し続けて自滅する（実測: 証明書で8周ストックした後に約17周を手で回した。
  予算を20000に上げてもターン探索が終わらなかった）。(2) 決定を1つずつ先読み評価で選ぶ
  方式では、探索なら実行できる XENARCH 型のループに入れず、サガ単独のループ
  （墓地型）に流れてしまった。

### 修正2: 仕込みの山札を実カードで構成する（`default_deck_cards`）

仕込み局面の自分の山札30枚＋シールド5枚を、中核の文明に収まる役割補完札
（search/draw/prep/accel/recover、コストの軽い順。basebuild の候補流用）と埋め札で

### 方式

方針（2026-11-25 ユーザー提示）: コンボ発見は ID の静的列挙ではなく、ID を排した
属性表現から求める。静的列挙の発見ランは v2・v3 とも新規エンジン0件だったため、
列挙の拡大ではなく、属性ベクトル空間の近傍（コサイン類似）で既知コアのカードを
置換する「既知コンボの一般化」を候補生成に使う。

- 種: サガ単独 {サガ×2}、サガ＋XENARCH {サガ×2, XENARCH×2}、アカシック最小コア4種
  （アカシック3×1、オルゼキア×2、ウォカンナ×1、ホーリーエンド×1）。
- 除外: 既知コアのカード自身と、v3 発見ランの既知コア集合（KNOWN_CORE 17種＋
  XENARCH＝18種）。加えて種と同名のカード（別セットの同名再録）は「同じカード」
  として除く。同名判定は既知コア18種の名前にも適用する（dmrp12-s01 は
  rules.cards のエイリアスで正規 ID は dm25sp1-003 のため、ID 照合だけでは
  再録を拾えない）。
- 置換パターン（候補129件）:
  - A サガ置換（25件）: サガの近傍カード単独×2。サガの役割を担える別カードがあるか。
  - B XENARCH 置換（40件）: サガ×2＋XENARCH の近傍×2。出力リソースを変える相方の一般化。
  - C サガ相方探索（24件）: サガ×2＋サガの近傍×2（うち1件は B と重複し統合）。
  - D アカシック置換（40件）: 最小コア4種のうち1種をその近傍上位10件に置換（各種10件）。
- 判定: 全候補を judge_engine3（予算1000・シード1）。合格したものは最小コアと
  増分を記録し、（最小コア, 増分）が既知エンジンと一致する場合は変換を再判定せず
  （v3 対照で確立済み）、新規性がある場合のみ judge_conversion3 で変換を見る。
  今回は新規性のある合格が無かったため、変換判定の実施は0件。
- D の後半20件は、1候補で探索が爆発し全体が止まったため、候補ごとに
  420秒のタイムアウトを付けて再実行した（タイムアウトは不合格ではなく未決着）。

- しかしループの相互作用は効果の正確な配線（どの誘発が・どのゾーン移動を・どの
  対象に）に依存し、属性の粗い類似では保存されない。決定的なのは B で、XENARCH の
  近傍40種のうち、サガの出力リソースを墓地から手札に変える相互作用を持つものは
  0種だった。XENARCH 本人の相互作用は、属性が似たカードには無い特異な配線だった。
- サガ自身は近傍の最大類似度が0.723と低く、属性空間でも孤立している
  （A の全滅と符合する）。アカシックは4種の機械仕掛けで、1種の置換では全て壊れた。
- 結論の範囲: 各種の近傍上位10〜40件・予算1000・シード1。属性近傍は候補の「族」の
  絞り込みには使えるが、エンジンの一般化には効果配線レベルの類似（束の移動・誘発
  構造の一致など、より細かい特徴）が要るという示唆が残る。

## 構造提案: 束の移動・誘発構造（構造署名）による候補生成（2026-11-25）

実装: `dmsim/discovery/structsig.py`（署名の抽出と走査）、実行:
`tools/combo_hunt3_struct.py`、テスト: `tests/test_structsig.py` 7件。
成果物は ~/workspace/combo3/（proposals_struct.jsonl / proposals_struct_retry.jsonl /
proposals_struct_retry_conv.jsonl / struct_signatures.json）。
判定は judge_engine3（予算1000・シード1）、候補ごとにサブプロセス隔離＋
タイムアウト明示。新規性のある合格は judge_conversion3 で変換まで見た。

### XENARCH の配線の特定

サガの回帰の出力を墓地型 {山札−1, 墓地＋1} から手札型 {山札−1, 手札＋1} に変えるのは、
XENARCH の4番目の能力（墓地誘発）である:

- 前提: 自分が墓地にいる間、自分の札が手札から墓地に置かれた時（move, from=hand,
  to=graveyard, subject={owner: you}）。
- 効果: 自分を墓地から手札に戻してもよい（move self, graveyard→hand）。

サガの周回には「ドロー→手札を1枚捨てる」が毎周含まれ、捨て先がこの誘発の前提に
一致する。実プレイの記録（仕込み局面からの探索、ログ98件）でも、周回ごとに
XENARCH のこの誘発（pending の能力番号3）が発火し続けていることを確認した。
捨てられた札が手札に戻るため墓地は増えず、ドロー分だけ手札が単調に増える。

束（loop_cond）の形では、前提 (move, hand→graveyard, {owner: you}, zone=graveyard) ＋
移動 (graveyard→hand, ref_self) という1束がこの配線の全てである。

不合格だった近傍との差分: 属性近傍で乗客だった《死神覇王 ブラックXENARCH》
（dm24ex3-rp2s05、類似度0.822）の墓地の束は、前提が (turn_end, self, zone=graveyard)
で効果は「自分のタップしたクリーチャー3体を破壊して自分を場に出す」であり、
hand→graveyard を受ける前提も graveyard→hand の自己移動も無い。名前・種族・
「墓地で働く大型闇クリーチャー」という族は同じでも、配線は全く別物だった。
もう1種の《凶怖覇王 ブラックXENARCH》（dm25ex3-rp3009）も、出た時の墓地肥やし＋
回収と「墓地を離れた時」の誘発で、傍受配線は無い。

### 構造署名の定義と走査結果（全11,477枚）

署名は束の前提（誘発イベント frm→to、主体、能力の働くゾーン）と移動
（src→dst、ref_self、draw、対象フィルタ）の組。部分署名の共有で候補を作る。

**傍受配線（XENARCH 型）**: 前提 (move, →graveyard, 主体は自分の札, zone=graveyard)
＋移動 (graveyard→hand または →bz) を含む束。ターン1回制限は同一ターン内の
多周回に追随できないため除外。全カード中の該当は25件のみ:

| 層 | 件数 | 内訳 |
|---|---|---|
| 厳密（移動元=hand、自己を手札へ） | 1 | XENARCH 本人のみ |
| 厳密・場戻し（移動元=hand、自己を場へ） | 1 | 《世露詞駆 キャロル》 |
| 移動元不問・自己を手札へ | 3 | 《電脳 ソルジャ-２》《Disデリンダー》《希望の覇王 鬼丸「刀」》 |
| 移動元不問・自己を場へ | 9 | ヘモグロ、ヘモグロ-2、ドゥコハン、阿修羅ムカデ、フッシッシ、シモーヌ・ペトル、ドゥリケン、フッシ-１、ハーシル |

自分に合わない）。draw＋discard だけの束は116件あり、緩すぎるため対象にしていない。

ほぼ全て「相手に捨てさせられた時（by: opp）」条件で自分の捨てる行為には反応せず、
戻し先も手札でないため、傍受の代替にはならない。

残り17件は全て乗客（最小コア {サガ×2}、墓地型）だった。層ごとの内訳:
場戻し層は10件全て乗客（捨てられた札が場に出るため手札には戻らず、出力変換に

自分自身に適合すること」に尽きた。適合しない6件の内訳: フィルタ不一致5件

ドラゴン・ゾンビで自分はトライストーン、デラスキヤンは戻しがコスト7以上で
自分はコスト4、ファルシとメギロンは戻しが呪文で自分はクリーチャー）と、
前提の理由制限1件（ムーンライトは破壊で墓地に行った時だけ＝理由 destroy）。
移動元不問・自己戻し層の《鬼丸「刀」》も理由制限（destroy のみ）で乗客だった。

つまり XENARCH の出力変換は「特異な1枚の配線」ではなく、「墓地で
手札→墓地（または自身の墓地着地）を受けて、自分を手札に戻す」という配線の
**族**だった。属性近傍では族の外見（大型・闇・破壊／蘇生系）しか拾えず
0件だったものが、構造署名では族ごと拾えた。反面、署名に入らない細部
（前提の理由制限 when.reason は束の Premise に載らない）が成否を分ける例も
2件あり、署名の粒度の限界も確認できた。

**サガ置換: 新規エンジン0件**。近接層3件は全て単独では回帰自体が検出されず
不合格。サガの自己回帰配線（出た時／ターン開始の draw＋discard＋自己蘇生＋
自分が墓地へ行く移動の4点セット）は、全カード中でサガだけのものだった。

### 所見

- 構造類似は「族」の特定には強力だった。傍受配線の族25件を全数走査でき、
  そのうち出力変換を再現する条件（自己戻し、または戻しフィルタの自己適合、
  理由制限なし）まで切り分けられた。属性近傍の結論（XENARCH の相互作用は
  特異）は、属性空間の範囲では正しかったが、構造では一般化できた。
- ただし再現したのは全て「サガのエンジンの出力変換」という一般化であり、
  エンジン骨格そのものの新規発見ではない。サガ型の自己回帰配線はサガのみ、
  という結果と合わせると、骨格の新規性は依然として高い壁である。
- 署名の限界: 前提の理由制限（when.reason = destroy 等）は束の Premise に
  載らず、署名では区別できない（鬼丸「刀」とムーンライトが該当）。
  次に署名を精緻化するなら、理由と移動の conds を署名に含めることが候補。
- アカシック置換の4件は、属性近傍の「族の絞り込み」が実は正しく、落ちていたのは
  判定時間の上限だった。候補生成（属性）と判定（v3）の役割分担として、
  属性近傍は D の範囲では機能していたと評価を改める。

### 陽性対照

- (a) サガ自己回帰: 厳密サイクルとして再発見 ✓（自己ループ辺あり、
  刈り込み通過も単体確認済み）。
- (b) サガ + XENARCH: 厳密サイクルとしては再発見できず ✗。辺は
  サガ→XENARCH のみで、戻り辺が無い。XENARCH の自己戻し（墓地→手札）は
  サガの前提（move→bz、主体 self）を満たさず、傍受は前提の連鎖ではなく
  カードの流れ（捨てられた札が手札に戻る）で効くため、原理的に有向サイクルに
  ならない。一方「前提閉集合」（組の全束の前提が組の中で満たされる）では
  再発見できた ✓。候補の単位はサイクル単独ではなく、サイクル＋前提を
  満たされる付随束（傍受・積み荷）への拡張が要る。
- (c) アカシック4種: 中心の回転 {オルゼキア呪文 ⇔ ナウ・オア・ネバー} は
  厳密な2束サイクルとして再発見 ✓。ウォカンナ誘発を加えた3束は前提閉集合 ✓
  （ウォカンナは前提を満たされるだけで戻り辺を持たない＝積み荷）。
  ただし (1) アカシック3 は束が0件（static の cast_free はグラフに現れない。
  マナ持続性の評価にもこの種のイネーブラが要る）、(2) 回転対の収支は
  '?' 移動のため静的検証不能だった。

  （コスト0またはサイクル自身がマナを生む）を課すと 1,530サイクル。
- 目視例: 厳密側は《ゾンビポンの助》+《ジーク・ナハトファルター》等の
  {場+1, 山札−1} 型（山札から場へ変換し続ける形）。多枚組側は
  《光輪の精霊シャウナ》を中心とする3〜4種の組が目立ち、形としては
  らしく見える。なお候補には試験用カード（T375 等）も混ざる（本実装では除外）。
- スポットチェック（ファネル上位10件に judge_engine_once、予算1000・シード1、
  各カード×2）: 10件全て判定が完走（38〜80秒/件）したが合格は 0件。
  提案→判定の接続は機械的に成立する一方、ファネル上位の静的精度は低い。

### 判定コストの見積もり

- 段階判定の単価: ファネル候補の judge_engine_once は実測 約45秒/件
  （スポットチェック中央値。ランダムペアの約7秒は即落ちの単価で、構造的に
  もっともらしい候補ほど重い）。最小化は合格時のみで 約300〜430秒/件（実績）。
- 規模別: 指定刈り込みのみの 582,810サイクルは約7,300時間で不可能。
  厳密ファネル（サンプルで66組、全数では数百組規模と推定）は段階1が
  約4〜6時間＋最小化で総 約10時間オーダーとなり実行可能。
  緩いファネル（約1.1万組）は段階1だけで約140時間超となり、追加の静的
  ふるいか並列実行（Kaggle）が要る。

### 結論: 調整すれば可能

グラフ構築（約6分）と長さ1・2の網羅列挙は実働し、陽性対照は
「サイクル＋前提閉集合」の形で3件とも構造的に再発見できた。一方で、
(1) 候補の単位を前提閉集合へ広げること、(2) alias 移動元の解決（'?' の解消）、
(3) static イネーブラ（無料化・コスト軽減）の表現、(4) マナ持続性を含む
静的ふるいの強化、(5) 長さ3・4の列挙アルゴリズムの改善（ハブ刈り等）が
本実装には必要で、指定した刈り込みだけでは候補が2桁多い。
スポットチェック 0/10 が示すとおり静的精度はまだ低く、判定器との
往復（expert iteration 的な還流）が前提になる。
