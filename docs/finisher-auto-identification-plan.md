# フィニッシャー自動特定システム 実装計画

作成: 2026-11-16（検討ドラフト。本文書は計画であり、実装済み機能の説明ではない）
位置づけ: システム完成を最優先とする方針の下で、「新規に取り込む価値がある」と判断した
Gemini 対話由来の唯一の大きな提案。既存の物差し（docs/combo-ruler-design.md）の
「段2: 勝利への変換」を、人が候補を指定しなくても測れるようにするための計画。

---

## 1. 目的と定義

- フィニッシャー（払い）: ループや資源生成で得たアドバンテージを、実際の勝利に変換する
  カード／行動の組。例: 絶望神サガループにおける
  《超神星DOOM・ドラゲリオン》＋《シャコガイル》の置換勝利、
  《シャコガイル》単体の置換勝利（場にいる状態で山札1枚ドロー）。
- 自動特定: 人が「このカードが勝ち手段のはずだ」と教えなくても、システムが
  カードプールから勝ち手段の候補を列挙し、検証済みのものだけを登録できること。
- 非目標: 完全な逆向き探索（勝利状態からの backward chaining 全般）は本計画に含めない。
  完成優先のため、まずは「候補列挙＋前方検証」の小さい形で入れる。

## 2. 現状の棚卸し（実装済み・設計済みの部品）

| 部品 | 場所 | 状態 |
|---|---|---|
| ループ証明書（win_by / needed / limit / delta） | dmsim/engine/loop.py | 実装済み。勝ちに直結するループは検出時に印が付く |
| ストック（fast_forward） | 同上 | 実装済み。周回数をパラメータとして局面を進められる |
| 2段探索（ループ→勝ち筋） | dmsim/search/loop_first.py | 実装済み。2段目は「与えられた局面から」勝ちを探す |
| 物差し 段1/段2 の分離 | docs/combo-ruler-design.md | 設計確定 v1（2026-11-13）。段2の測定器は未実装 |
| 勝ち手段の個別判定 | dmsim/search/access.py の draw_win 等 | 個別ルールとして実装。汎用の分類器ではない |
| 常在の勝利条件の距離 | dmsim/search/leaf_eval.py goal_distance | kind: state の「ゲームに勝つ」効果は評価関数が認識する |
| 部品固定の探索 | dmsim/discovery/combo_search.py search_setup | 「足す1枚」を総当たりで測れる（候補は人が pool で渡す） |

不足しているのは「勝ち手段の候補を、人の指定なしに列挙する」層だけである。
探索（2段目）も登録先も既にある。

## 3. 設計: 3つの列挙経路

### 経路A: 効果タイプによる静的分類（最初に実装する）

カード定義（DSL）の効果を走査し、終端に効く効果を持つカードにタグを付ける。

- `win` op を含む（「ゲームに勝つ」効果）→ タグ: `replace_win` / `direct_win`
- 相手への直接の終端圧力: シールドを0にする攻撃力の源、相手の山札を直接減らす効果、
  ダイレクトアタックを可能にする効果 → タグ: `terminal_damage` 系
- 置換効果のうち「敗北を勝利に置換する」もの → タグ: `replace_win`
- 分類は DSL の op と対象（player 指定）だけで決める。カード名・テキスト解釈は使わない
  （変換ミスを最初に突くのは自動検証の役目。人手の意味付けはしない）。
- 出力: `data/registry/finisher_candidates.yaml`（カードID、タグ、根拠となった op パス）。
  生成物として再生成可能にし、手編集しない。

### 経路B: スケーラビリティ検査（無限リソース下の試行）

Gemini 対話の「無限リソース状態で1枚ずつ試す」案を、既存部品で実現する。

1. ループ証明書から「ストック済み局面」を作る（fast_forward で limit まで進めた局面）。
   ループが無い文脈では、scenario で資源を潤沢にした固定局面を使う。
2. 経路Aの候補（および未分類カード）を1枚ずつ、その局面の手札／場に足す。
3. 2段目の探索（loop_first の seek、または TurnSearch）で勝ちに届くか測る。
4. 届いたカードを「このループに対する有効なフィニッシャー」として記録する。
   記録にはループの署名（証明書の骨格＋delta）と必要周回数を必ず含める
   （フィニッシャーはループと独立には定義できないため）。

### 経路C: 終端からの逆引き（将来・本計画では実装しない）

勝利状態から1手前を逆算する方式。エンジンが前方実行専用（タスクスタックの逆再生が
ない）ため、実現には逆向き遷移の新基盤が要り、完成優先の方針と合わない。
経路A+Bで候補が漏れる実例が出た場合にだけ再検討する。

## 4. 出力スキーマ（既存形式に合わせる）

新規フォーマットは作らず、登録簿（registry）の既存形式に1種別を追加する。

```yaml
# data/registry/finishers.yaml（生成物）
- card: dm22ex1-007            # ドラゲリオン
  tags: [terminal_damage]      # 経路Aの分類
  verified_with:               # 経路Bの検証結果
    - loop_signature: saga_burn_m1_g1     # 証明書の骨格＋delta から作る署名
      needed_stock: null                  # 周回数が条件でない場合は null
      setup: tests/saga_setup.yaml        # 再現可能な開始局面
      result: kill                        # kill / no-kill / unknown（全探索の3値と揃える）
      nodes: 27                           # 事後報告値（制限ではない）
  source: auto                 # auto / human（人手登録と区別する）
```

- `result` は勝ち／勝ちなし（証明済み）／未証明の3値にする。通常探索の結果は
  「未証明」として記録し、「勝ちなし」と混同しない（物差しの校正方針と一致させる）。
- スキーマは data/schema/ に JSON Schema を追加して検証可能にする
  （カード系スキーマと同じ運用。詳細は出力・スキーマ見直しの検討と連動）。

## 5. 実装ステップ

1. **分類器（経路A）**: `dmsim/discovery/finisher_classify.py`（仮称）。
   全変換済みカードを走査して候補 yaml を生成。単体テスト:
   既知の勝ち手段（シャコガイル、ドラゲリオン、テスト用プロトカードの win 効果）が
   必ず候補に入ること（陽性対照）。
2. **検証ハーネス（経路B）**: loop_first の seek を再利用し、候補×既知ループ
   （サガ、テンモン等の登録済みループ）の組み合わせを測る CLI。
   既知フィニッシャーが kill になり、無関係カードが kill にならないことをテスト化。
3. **登録と回帰**: 検証を通った組を registry に登録し、通常の回帰テスト
   （test_saga_discovery 等）と同じ仕組みで再検証できるようにする。
4. **combo_search との接続**: 部品固定探索の pool 提案に、フィニッシャー候補を
   優先的に含める（pool 全体を測る前の絞り込みとして使う。pool の決定権は従来どおり人／呼び出し側）。

各ステップは独立にマージ可能で、ステップ1だけでも「候補一覧」という成果物が残る。

## 6. 検証基準（完成の定義への接続）

- 陽性対照: 既知の勝ち手段がすべて候補に挙がり、既知ループとの組で kill が再現する。
- 陰性対照: ランダムなカード組では kill が出ない（validity の既存ゲートと同じ考え方）。
- 物差しとの対応: 本システムの出力は物差しの段2（勝利への変換）の入力になる。
  段1（ループ成立）の測定は変えない。
- 再現性: すべての検証は scenario＋シードで再生可能にする（既存方針どおり）。

## 7. リスクと保留事項

- DSL変換の誤りは分類にも伝播する。分類結果は「候補」であって「確定」ではない。
  確定は必ず経路Bの実行検証を通ったものだけにする。
- 「相手の山札を削る」系は、ループ自体が勝ち手段になる場合（deck_out）と
  混同しやすい。タグでは burn（ループ側）と finisher（変換側）を分ける。
- 妨害モデルが簡易な現状では、相手の対応を前提にしたフィニッシャー
  （トリガーケア等）は評価できない。対象は1人回しの範囲に限る。
- 経路C（逆向き探索）と、信念状態を前提にした特定は、本計画の範囲外（完成後）。

## 8. 未決事項（ユーザーの判断が要る点）

- フィニッシャーの登録を registry の正本に含めるか、生成物として都度作り直すか。
- 経路Bの検証に使う探索: 通常探索（予算つき）で足りる組が大半だが、
  「勝ちなし」の確定には全探索（試作中）の3値結果を使う想定でよいか。
