# フェーズに合った段階目標の鎖：責務の検討と生成自動化の計画

作成: 2026-11-17（検討ドラフト。本文書は計画であり、実装済み機能の説明ではない）
位置づけ: docs/order-function-generalization-plan.md §3.5 の実測を受けた下位計画。
関連: docs/exhaustive-search-saga-report.md §5.9（Plan を保持に接続する実験）、
dmsim/plan/macro.py（大局観）、dmsim/plan/stagegen.py（鎖の生成）、
dmsim/plan/combo_sequence.py（検証済みコンボの登録）。

---

## 1. 課題

§5.9 の実測で、保持の判断に大局観の Plan を使う成否は「鎖が局面のフェーズに
合っているか」で決まった。既存の生成チェーンは部品集めフェーズ専用であり、
ループ実行フェーズの鎖が存在しない。必要なのは次の3点:

1. フェーズ（部品集め／実行／仕上げ）に合った鎖を、コンボごとに用意できること。
2. その鎖を手書きでなく自動生成できること（コンボが増えるほど手書きは破綻する）。
3. 生成した鎖を採用前に検証できること（悪い鎖は V 順序より保持を悪化させた）。

## 2. なぜ既存の生成（stagegen）では実行フェーズの鎖が作れないか

stagegen の入力は LoopSpec の最小盤面 M か combos.yaml の leaf_parts で、
どちらも「最終盤面を満たす部品の集合」という**静的な最終状態**の記述である。
生成方法も、ゾーン順に部品を1つずつ足す累積で、最終盤面への到達だけを見る。

実行フェーズの進みは最終状態ではなく**軌跡の性質**（墓地が12→16→21枚と育つ、
フィニッシャーが山札→手札→場と移る、山札が減っていく）なので、
入力にも生成方法にも表現する場所がない。加えて2つの構造的な制約がある:

- stagegen は deck の述語を捨てる（山札の中身は非公開情報という公平性の規則）。
  ただし「自分の山札の残り枚数」は公開情報であり、名前つき述語と
  枚数だけの述語（"*"）は分けて扱う余地がある（§5 で要明確化）。
- 累積目標は単調なため、「部品を手札に揃える→投入して手札から消える」
  というフェーズ跨ぎで進捗が後退して見える（§5.9 の生成チェーンの失敗は
  この一例）。MacroPlanner は「最初の未達の段」を狙うので、
  投入で未達に戻る段があると充足率が崩れる。

## 3. 責務の検討（どこが請け負うか）

候補を既存のレイヤ（S3=探索・プレイ／大局観、S5=発見、registry=共有の保管）に
照らして判定する。

| 役割 | 請け負う場所 | 判定と理由 |
|---|---|---|
| 鎖の**消費**（現在の段の判定） | 大局観 MacroPlanner（現行のまま） | 変更しない。Plan の形は「どの出し手でも同じ形」が設計原則で、判定と目標設定を同じ場所に混ぜない |
| 鎖の**形式への変換**（コンパイラ） | stagegen（dmsim/plan、S3） | 現行の役割の拡張。生成物のヘッダが言う通り「手で直さず、元データを直して作り直す」場所。新しい入力種別（軌跡）を足す |
| 鎖の**元データの著者**（中継点の抽出） | 発見・登録側（S5→registry 登録経路、combo_sequence の後続） | 検証済みの手順（記録）を持つのはこの側だけ。combo_sequence.py 自身の docstring が「発見した手順から段階目標を作る後続の仕事」と明記しており、既存の設計意図とも一致する |
| 鎖の**保管** | registry（PlanSpec.params["stages"]）と data/eval/stages/*.yaml（現行の置き場） | 変更しない。大局観 S3 と発見 S5 が読む共有物という registry の位置づけに合う |
| 鎖の**採否の検証**（ゲート） | 評価側の道具（tools、vgate の鎖版） | V の重みに vgate があるのと同じ構図。生成と採否を分け、悪い鎖を標準に混ぜない |
| **共通ガード**（生存: 次のドローで負けない等） | 当面は生成時に全鎖へ差し込む共通段として stagegen が担当 | コンボ固有ではないので各コンボの元データに書かせない。Plan 形式に guard を足す案は形式の版上げが要るため、必要性が実証されてから別途検討する |

結論: **新しい部品は作らない**。足りないのは (a) 登録側が検証済み手順から
中継点の元データを出す仕事、(b) stagegen の入力種別の追加、(c) 鎖ゲート、
の3つであり、いずれも既存の責務の延長に置ける。

## 4. 自動生成の方式（検証済み手順の軌跡から中継点を抽出する）

入力: そのコンボの検証済み手順の記録（make_record 形式。再
生可能なものだけを使う。combo_hunt の検証済み結果、全探索のキル記録、
reach_chain の到達記録が候補）。

手順:

1. **再生とスナップショット**: 各記録を再生し、自分のターン境界ごとに
   ゾーン枚数ベクトル（部品の所在と各ゾーンの "*" 枚数）を取る。
   あわせて「その局面から何ターンで殺せたか」をラベルにする。
2. **中継点の抽出**: 勝ち軌跡に共通する通過点を段にする。
   - 部品の所在: 最終盤面・最小盤面から（現行 stagegen と同じ材料）。
   - 枚数の閾値: ターン境界の "*" 枚数について、キルまでの残りターンごとに
     分布を見て、勝ち軌跡が確実に通過する水準（例: 残り2ターンの局面の
     最小値）を段の閾値にする。サガの実測では墓地 12→16 がこれに当たる。
   - 順序: 段は「先に満たされるものが手前」に並べる（軌跡での達成ターンの
     中央値でソート）。累積（前の段の条件を含む形）に直すのは stagegen 側。
3. **共通ガードの差し込み**: 生存などの共通段を先頭側に差し込む（§3）。
   ただしガードは「満たし続ける」性質のもので、累積の単調性とぶつかる
   場合は段でなく充足率の計算側の扱いを分ける（§6 の未決）。
4. **ゲート検証**: §5 の鎖ゲートを通ったものだけを .generated として出す。

注意: 記録が少ないコンボでは閾値が不安定になる。記録数と閾値の根拠
（何件の軌跡から出したか）を生成物に併記し、少ない場合は部品集めの鎖に
フォールバックする（実行フェーズの段を作らない）。

## 5. 鎖ゲート（採否の検証）の設計

今回の実験で使った2つの測定を定型化する:

- **診断**: 代表シナリオのターン境界局面に充足率を付け、最速キル局面の
  充足率順位を出す（tools/plan_leaf_diag.py が原型）。生成チェーン（部品集め）
  より悪ければ不採用。
- **保持テスト**: beam（幅4）を絞った横断探索で、最速キルの保持と
  ノード数を現行の標準（順序関数 v2、または既存の鎖）と比較する。
  悪化する鎖は採用しない（vgate が「base を上回った候補だけ残す」のと同じ規則）。

## 6. 表現力の不足と対処

- **フェーズ跨ぎで累積が崩れる**: 部品の投入で手札の条件が未達に戻る。
  対処の候補は3つ。(a) フェーズごとに鎖を分け、大局観が局面に応じて
  鎖を選ぶ（鎖の選択も大局観の仕事に含める）。(b) 段の目標で
  「いずれかのゾーン」を表せるよう形式を拡張する。(c) 生成側で
  「手札または場または墓地」の合算に変換して吸収する。
  当面は (a)（形式を変えず、鎖を分ける）で進め、実測で不足が見えたら
  (b) を検討する。
- **deck 述語の公平性**: 名前つき述語（中身）は従来通り捨てる。
  自分の山札の残り枚数（"*" の枚数）は公開情報として使えることを、
  stagegen の規則として明記する。相手側は従来通り全て捨てる。
- **上限のある条件**（「山札が多すぎない」等）は reach_target の
  下限述語では書けない。必要になった場合は形式の拡張として別途扱い、
  鎖データに無理に埋め込まない。

## 7. 段階計画

1. 段1: 抽出器の試作（§4 の 1〜2）をサガで作る。材料は検証済みの
   キル記録（全探索の20件＋横断探索の記録）。手書きの実行フェーズの鎖
   （tools/saga_loop_stages.yaml）と同等以上の診断結果が出るかを見る。
2. 段2: 鎖ゲートの tools 化（§5）。診断＋保持テストを1コマンドにする。
3. 段3: stagegen に軌跡入力の種別を追加し、gen_stages.py から
   実行フェーズ込みの .generated を出せるようにする。あわせて
   combo_sequence の stages を「部品が手札にそろう」1段から、
   登録時に軌跡由来の段を含む形へ拡張する。
4. 段4: サガ以外（天門など、鎖と記録が既にあるもの）で生成→ゲート→
   保持テストを通し、方式がコンボ固有でないことを確認する。
5. 段5: 大局観の鎖選択（§6 の (a)）を MacroPlanner の利用側
   （保持と V の計画項）に接続し、フェーズで鎖が切り替わる形にする。

## 7.5 実測（2026-11-17）: 段1・段2 の試作と結果

- 抽出器（tools/chain_extract.py）を実装。検証済み記録11件（横断探索の
  frontier 記録）を再生してターン開始局面を集め、鎖を自動生成した。
  抽出された鎖は「イワシン・シャコガイルが墓地 → 山札ガード＋墓地12枚 →
  墓地13枚」の3段で、手書きの実行フェーズの鎖に近いが、ドラゲリオンの
  手札条件は入らなかった（キルターン開始時点では未所持の記録があるため）。
- 鎖ゲート（tools/chain_gate.py）を実装し、抽出チェーンと対照の
  生成チェーン（部品集め）を判定した:
  - 抽出チェーン: **PASS**。診断では最速キル局面の充足率順位は 1・3・8位
    （手書き版の 0・1・2位より弱い）が、beam4 の保持テストでは hidden・prep
    ともに全シードで2ターンキルを保持し、ノード数も基準（順序関数 v2）と
    同等だった。
  - 生成チェーン: **FAIL**（hidden で3ターンキルに劣化）。既知の判定を
    ゲートが再現したことで、ゲート自体の妥当性も確認できた。
- 学び: 保持に必要なのは診断順位の完全な一致ではなく「beam 幅の中に
  最速キル局面が残ること」であり、閾値が粗い抽出でも実用になった。
  一方で診断順位の弱さは抽出の改善余地（キルターン開始でなく
  ターン終了局面もスナップショットに含める等）として残る。

## 8. 未決事項

- ガード（生存）を段として差し込むか、充足率の計算から分離するか。
  段にすると「満たし続ける条件」が累積の前提と衝突しうる。
- 閾値の決め方の詳細（残りターンごとの最小値か、分位か）と、
  記録が何件未満なら実行フェーズの段を作らないか。
- 鎖の正本は registry（PlanSpec）と data/eval/stages のどちらに置くか。
  現状は両方が存在する（生成は yaml、登録は PlanSpec）。統合するか、
  片方向の生成関係にするかの整理が段3の前提になる。
