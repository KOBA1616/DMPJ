# 検証済みコンボの登録簿（ロードマップ P2「登録簿」、2026-11-13）

## 1. 窓口の約束
- 入力: 候補（`dmsim.base.registry.Candidate`）= 中核の札・型・勝ち方・入口局面か手順・区分・測り方（シード・ターン上限・budget）。
- 出力: 照会 `registry.query(types=, split=, for_tuning=, core_id=, win=)`。大局観 S3 と発見 S5 が読む。調整に使う経路は `for_tuning=True`（holdout を出さない）。
- 書き込み: `dmsim.eval.verify.register` だけ（中で `registry.record` を呼ぶ）。`record` は S4 の検証役が出した `Evidence` で、候補と同じ指紋のものしか受け付けない。`record` を呼ぶのが verify.py だけであることを `tests/test_registry.py` が確かめる。
- tuning / holdout / discovered: `split` で区別。holdout は `purpose="tuning"` で書くと `HoldoutWriteError`（`base/store.check`）。

## 2. 置き場と項目
- 型: `dmsim/base/registry.py`（S0、他層を import しない）。
- 候補: `data/registry/candidates.yaml`（人が書く）。元は `data/known_combos/combos.yaml` と `data/discovered_combos/combos.yaml`。どちらも形を変えていない（日次の自動実行が読む）。
- 登録簿: `data/registry/combos.yaml`（`tools/registry.py` が書く。手で書き換えない）。`entries`（通過）と `rejected`（落ちた候補と落ちた検証 `failed_at`）。
- 1件の項目: id・name・split・types（loop/resource/attack/lock、重複可、設計書 §11）・core（id・name・役割）・win（opp_deck_out/effect/lock/beat）・entry（入口局面）か procedure（手順の文）・lock_mode・seeds・max_turn・budget・digest（候補の指紋）・checks（各検証の合否と説明）・measured（段1・段2の到達率、勝ち方の内訳、勝ったターン、シードごとの行）・version（測定器とカードデータの fingerprint、commit、日付）。
- fingerprint が今と違う行は古い（測り直しの対象）。今は照会で弾かず、読む側が version を見る。

## 3. 検証（`dmsim/eval/verify.py`）
順に行い、最初に落ちた所で止める: cards（中核の札がカードデータにある）→ type（今の物差しで測れる型か）→ entry（入口局面がある）→ ruler（`ruler_control.run_one` と同じ測り方で各シード1局、段2到達率 ≥ 陽性対照の KNOWN_MIN=0.8、対局の失敗なし）→ replay（先頭2シードを回し直して開始局面の指紋・段1・段2・勝ち方・勝ったターンが一致）。閾値・budget は既存の値のまま（数字を合わせる調整はしない）。

### replay・shrink を S4 に寄せる計画
- すでに S4: `eval/replay.py`（手順の再生 replay_test）、`eval/shrink.py`、`eval/reproducibility.py`、`eval/lockcheck.py`（discovery 側は旧名の互換だけ）。
- 下の層に残るもの: `engine/loop.py` の `verify`・`replay_keys`（ループ証明書の再生、S2）、`engine/play.py` の `replay`・`replay_record`（ログの再生、S2）、`search/pattern_loop.py` の `replay_counts`（S3）。これらは下の層の部品なので移さず、S4 の verify から呼ぶ形にする。
- 次の段（今回は未実装）: (1) 登録時に勝った局の手順（`replay.steps_of`）を保存し、`replay_test` で手順の再生も確かめる。(2) `shrink` で入口局面の最小化をして core の自動抽出と突き合わせる。(3) 能動ロックの自分の方針（`lockcheck.prefer_policy`・探索）を候補に持たせて `make_full_lock_judge` で測る。

## 5. 新規性判定（範囲）
`registry.novelty(候補)`: 登録済みと落ちた候補の中核の札の集合を比べ、same／superset／subset／overlap と、勝ち方が同じかを返す最小版。H.D.2. 版は既知アカシックと overlap（アカシック3・訪れる魔の時刻が共通、勝ち手段が違う）。
次の段（未実装）: 仕組みの比較（入口局面の 1周の差分 delta と勝ち方が同じなら同じ仕組み）、代わりのある組（loop_entry.core_groups の any）を考えた比較。

## 8. ドリル＋ジョバンニ＋クルトを実デッキで測り直し（2026-11-13、holdout、登録を取り消し）
**作り直した成立局面**（data/registry/setups/drill_lock.json）: 実デッキ data/decks/drill_lock.yaml（中核3種×4枚＋効果を持たない光・火の実在クリーチャー28枚。既存の実戦デッキが無いので作った。試験札なし）。場にジョバンニ、手札にドリル・スコールとクルト、マナに火2・光3。手札の残り3枚・盾5枚・山札の並びはシードで配る（開始局面 8シードで8種）。相手はマナ6枚、デッキは相手の段階（`search.opponent.resistance`）。
**与えた方針**（候補の policy / policy_avoid に記録）: マナ置き用の札をチャージ → ドリル → クルト（墓地のドリルを山札の上へ）→ ドリルで捨てる自分のマナはマナ置き用 → ジョバンニで墓地のクルト・ドリルを手札へ。コンボの札はチャージしない。holdout なので方針の調整はしていない。

**結果: 段階0 0/8、段階1 0/8。全局「相手の資源が増えた」で破れた**（破れたのは自分の3〜19ターン目、自分の山札は 9〜25 枚残り）。登録簿からは外し、rejected（failed_at: lock）に残した。
- 原因（手順を1局追って確認）: ドリル・スコールは自分のマナも1枚墓地へ置く。クルトでドリルを山札の上に戻すと、次のドロ－はドリルになり新しい札が来ないので、チャージする札が無い。自分のマナが毎ターン1枚減り、火か光が尽きた時点でドリルかクルトが唱えられず、相手のマナが増えて破れる。
- クルトの役割: 自分の山札を減らさない（ドローがドリルに置き換わる）代わりにマナを削る。クルトを使わない方針も試した（参考、記録外）: 段階0 で 2/8 が自分の山札切れ負け、6/8 が同じ破れ。新しい札を引いてチャージできる分マナは保つが、山札が1枚ずつ減り、相手と同じ速さで尽きる。
- 前回の 8/8 の正体: 山札が全部試験札（チャージ用の札）だったので、毎ターン引いた札をチャージでき、自分のマナが減らなかった。実デッキでは起きない。
- 相手のマナが6枚で固定されること: カードの挙動としては正しい（ドリル1回で相手のマナ −1、相手のチャージで +1）。ただし相手は段階0・1とも自分から札を出さない（段階1は盾の S・トリガーとブロックだけ、`resistance` の説明どおり）。実戦の相手は6マナで除去（ジョバンニを破壊）などができるので、仮に回り続けても「相手を動けなくするロック」にはなっていない。段階1は、自分が攻撃しない（盾を割らない）ロックでは段階0と同じ結果になる（今回も同じ）。相手が出して殴り返す段階2は未実装。
- 仕組み（verify）: 能動ロックの setup に deck（実デッキ）があれば、手札の残り・盾・山札を `resource._deal` と同じ流儀で配る。候補の `opp_levels` の全段階で基準を満たしたら通す。`lockcheck.prefer_policy` に `avoid`（合っても選ばない key の先頭）を足した（既定は空で、従来の呼び出しは変わらない）。試験札の旧局面は単体テスト専用 data/registry/setups/drill_lock_dummy.json に移した。

## 9. 登録簿の手順を探索が使う口（2026-11-13、ロードマップ P3「探索にループ実行の手」の入口）
- 読む側（S3）: `dmsim/search/macro.py`。S0 の `registry.query(for_tuning=True)` だけを読む（holdout は出ない。S4/S5 は import しない）。
- 手の中身: 登録簿の項目の entry（入口局面の minimal）と、登録時に S4（verify の ruler 段）が記録した `measured.macros`（入口のターン＝自分の1ターン目に勝った局ごとに、最初のチャージを除く自分の決定の (種類, 選んだ意味キー) の列。最大8本。ループの周回と勝ち手段を含む）。
- 探索への口: `TurnSearch._macro_children` を候補を並べる前に1か所だけ足した（並べ方・払い方には触れていない）。局面が入口の条件を満たせば、複製で手順を実際のエンジンで再生し、成立した子を通常の候補より先に探索する。1回の run で試す局面は `macro.MAX_NODES`=4 個まで。
- 再生の規則（`macro.replay`）: 相手の決定は探索と同じ相手役。手順に無い決定（チャージや順番の違う確認）は探索の候補のうち中核の札に触れない最初の選択で答える（20回まで）。中核の札を含む選択（錨）が選べなければ不成立。払い方・中核に関わらない選択は探索の方策に任せる。ターンが終わる・手順を最後まで再生して勝っていない場合も不成立。採った線には `source: registry` のループの記録を残す（段1の記録。周回数は主張しない）。
- スイッチ: 既定は無効（`macro.enable()` か環境変数 `DMSIM_REGISTRY_MACRO=1`）。無効なら TurnSearch は従来と同じ。
- 経路の段: `registry.route_stages(ref)` が data/loops/route/ の名前・パス・段のリストを読む（形式はそのスレッドに合わせ、今は読むだけ）。

**効き目**（`tools/macro_effect.py`、予算200、相手は無抵抗）。入口局面は登録の検証に使ったシード1〜8と重ねない 9〜24:
| 対象 | 手なし 段2 | 手あり 段2 |
|---|---|---|
| アカシック 入口（ばらつきあり） | 2/16 | **16/16** |
| サガ 入口（ばらつきあり） | 12/16 | **15/16** |
| サガ 通常開幕40局（上限6ターン） | 0/40（殴り37、入口到達0） | 0/40（同じ） |
| アカシック 通常開幕40局 | 0/40（殴り7、入口到達0） | 0/40（同じ） |

通常開幕では、どちらのコンボも入口まで届かないので手が使われない（入口に届かせるのは経路の段の作業）。入口局面の数字は登録簿の手順を再生したもので、入口に届いた後の「ループを選び切れない」問題（探索側）を手が補えることを示す。手順は登録に使ったシードの手札で記録したものだが、中核の札に関わらない選択は探索に任せるので、別シードの局面でも成立する（上の 9〜24）。

## 10. 中核をループ部品と勝ち手段に分ける（2026-11-14、combo-ruler-design.md §23）

- `Candidate.core` の各札に `part: loop|win`（既定 loop）。`core_ids(part)` で絞る。
- 手順の記録 `measured.macros[].loop_end`: 勝ち手段の札に初めて触れる手の位置。そこまでがループ部分、以降が勝ちへの変換部分。
- 新しい入口（ループ部品だけ）で測ると、saga 段2 1/8・akashic 3/8・akashic_hd2 6/8（max_turn 2。4 でも同じ）で3件とも基準 0.8 未満。
  勝ち方の内訳: saga は殴り6・ループ1、akashic はループ3・決着なし5、akashic_hd2 はループ6・決着なし2。
  段2が直るまで、登録簿は旧い入口（`*_v1.json`、誤った定義）で検証する（data/discovery/entry_min/registry_turns.json）。
