# 評価関数 V の設計（2026-11-10 koba と合意）

状態: **設計のみ・未実装**。現状との差は §6。決定の経緯はプロジェクトチャット（内部AIのスレッド）。

## 1. 目的
3〜4ターンキルを目的に、探索の**順位づけ**を助ける。足切り（局面を捨てる判断）には使わない。公平探索（相手の山札・盾の中身を見ない）の情報だけを使う。

## 2. 入出力
- 入力: 局面の特徴量 + **計画**（大局観システムから）。
- 出力（別々のヘッド。1つの数に混ぜない）:
  1. **T内勝率** V(局面, 計画) = その局面から、その計画に沿って打ったとき T ターン以内に勝つ確率（T=3,4,…）。
  2. **再現性確率** = 同じ計画が別の山札順・先後・相手でも成立する確率（決定化した多数の山札順での成功率の分散・下限で測る）。
  3. **コスト対総合パフォーマンス** = §4。
  - 補助出力: 小目標の鎖の各段への到達確率（勝ちが出ない対象でも学習できる）。

## 3. 特徴量
- 盤面（静）: 自分の場・手札・マナ・墓地、相手の盾・山札の枚数など。
- リソース（静）: 手札・マナ・盾の枚数、**盾の束**（盾の下の合計枚数・最大の束・束のある盾の数）、部品の所持。
- 効果スタック: 待機中の効果、S・トリガーで出うる札、ブレイクで起動する効果、**場で有効な継続効果（ロック類）**と、それが相手の「できること」を減らした量。
- 期待状態: 計画が成功したときの次の状態（小目標の次の段）と、現在との差（あと何段か）。

## 4. コスト対総合パフォーマンス
- 分母: 使用マナ（マナ0の手は、手札・場の札の消費をマナ換算で加える。重みは小さく始める）。
- 分子: 起きた現象の種類別の和（内訳ベクトルと重み付き合計の両方を残す）。
  - リソース増減（手札・盾・盾の下・マナ・墓地）
  - 盤面強化（場の数・パワー・ブレイク数・ブロッカー）
  - 妨害・除去（相手の資源・クリーチャー・盾の破壊）
  - ロック: 行動の制限（プレイ・攻撃・ブロックの制限）、起動の妨害（能力の無効化・誘発の抑止）、無効（打ち消し・置換）、資源の枯渇（マナ全破壊・山札切れへ向かう）
- ロックの測り方: 相手の合法手の数と、相手が実際に使えるカードの数の、前後の差。
- **場にいる間続く効果**（常在型の静的能力）は一度きりでなく、「場にいるターン数 × 減らした「できること」」を累積する。離れれば消える。除去されやすさは相手モデルが簡易なため未対応。
- 重みは、最初は人が決めた小さな表。後で、既知コンボの再発見に必要な探索量が減るよう進化的に調整する。

## 5. 計画（大局観との連携）
- 連携は API でなく**直接（同一プロセス）**。V は探索で局面ごとに何万回も呼ばれ、遅れを増やさないため。
- 計画の形は版つきのデータ `Plan`（狙い intent、目標部品、小目標の鎖と現在の段、予算）に固定する。MacroPlanner（規則ベース v1、docs/loop-discovery.md）、将来の学習版、逆算の展開器（notes/combo-loop-discovery-design-20261110.md 手順3）のどれが出しても同じ形で渡せる。Rust 化の境界にもなる。
- 学習データは (局面, 計画, 結果) の組。

## 6. 現状（実装済みのもの）との差
- 手で決めた `evaluate`（dmsim/solitaire.py）と `priority`（dmsim/discovery/bestfirst.py）: 静的な盤面と枚数の重み和 + 待機中の効果数 + 自盾の枚数（ゴール札があるときのみ）。局面が変わるたび候補ごとに計算する。収支・継続効果・束・計画の項はない。
- 学習した V（dmsim/autofix/valuelearn.py）: 線形リッジ回帰。特徴は枚数と部品の所持のみ。ラベルは -(キルターン)。順位づけの加点（learned_mult、初期 0）。日次の調整で再学習。勝ちが出ない対象ではラベルがほぼ一定で学べない。

## 7. 採否の基準と注意
- 新しい V を入れたとき、既知コンボ（天門など）の**段階到達率**が手で決めた評価と同じか上がること。下がるなら採用しない。
- 測定器・効果データが変わったら、古い学習データは無効にして学び直す。
- 探索の長さ（ターン上限）で結果が大きく変わる（天門: 8ターン上限では 0/8、14ターンで 8/8）。測定ではターン上限を明記・固定する。
- 保留: 相手モデルを `charge_only` から実際にカードを使う簡易方策へ変える（ロックの実害を測るのに必要）。

## 8. 採否ゲートの実装（2026-11-10）
- `dmsim/eval/vgate.py` / `tools/v_gate.py`: 段階目標の鎖（`data/eval/stages/<コンボ>.yaml`）への到達段階数を、base（手で決めた順位づけ）と `v_priority` の重み候補（under_w, res_w）で、同じ seed・同じ強制開始（先頭の段の札を手札に入れ替える `engine_view.force_hand`）から比べる。base を**上回った**重みだけ `data/autofix/vweights.yaml` に残す（同点・下回りは採らない）。日次（auto_fix `--total-seconds`）で段階目標のあるコンボ1件あたり 300 秒を確保して回す。
- 初回の実測（鎖の前段の到達局面から続ける方式。tenmon、8 seed、幅150、14ターン上限、forced 3枚）: base も V の4候補（3/1, 6/1, 6/3, 10/3）も合計12段階で同じ（seed ごとの到達も同一）。V の特徴量（盾の束・資源総量）はこの鎖の最初の2段（エメラルーダ登場・天門を唱える）の探索順位を動かさない。差が出るのは盾の束ができる段（tenmon_in_shield 以降）に届く局面だが、鎖がそこまで届いていない（多くの seed が2段目で止まる）。次の課題は2段目の突破（鎖が前段の到達局面から続けて探すため、個別測定の 8/8 より低い）。
- **鎖の2段目が届かない原因（2026-11-10）**: 段1（エメラルーダを場に出す）の最短経路が、後ろの段の札（天門・ミルザム）を手札から使い切ってしまい、段2（天門を唱える）が、鎖では届かない（単独なら 8/8）。対策: `reach_chain(keep_later=True)` は、後ろの段が要る札で手札にあるものを残したまま届く局面を先に探す（届かなければ元の目標）。tenmon 8 seed の合計到達段階は 12 → 17（1 seed は 4 段）。段3以降は残課題（マナ・盤面の資源）。時間は約2.6倍（37秒→98秒/8 seed）なので、日次の枠は 450 秒・seed 6 に調整。vgate は keep_later=True で測る。
- **段3以降（2026-11-10 続き）**: ミルザムはコスト9で、ヘブンズ・ゲート（天門）が場に出す札。前段が天門を単独で唱えてしまうと、次段「ミルザムを場に出す」はマナ5〜6では届かない。`reach_chain(keep_later=True)` は、前段に続けて次段を試し、続けられなければ「前段＋次段を合わせた目標」を一度に探す（`_merge`）。また、残す札の条件から、その段の目標に出る札を除いた（目標と手札に同じ札が二重に要る矛盾を避ける）。tenmon 8 seed の合計到達段階は 17 → 21（最大5段）。残る課題は、盾に天門を入れる段（エメラルーダの手札シールド化）以降と、マナ（9枚）の確保。
- **先読み（2026-11-10 続き2）**: 前段の手が次段の手を兼ねるかは、1手先では分からない（窓を広げて合わせる方式は、先に天門を単独で唱える合わせ方を選んで 16 に悪化）。`reach_chain(keep_later=True)` は lookahead=3 手先まで読み、「keep で1段進む」「次段と合わせて2段進む」の候補のうち、進める段数が最大のものを選ぶ。tenmon 8 seed の合計到達段階: 21 → 31（5 seed が 4 段＝盾に天門を入れる段の手前まで、1 seed が 5 段）。1 seed あたり約 9〜25 秒。次の詰まりは『盾に天門を入れる』段（エメラルーダの手札シールド化）で、V の盾の束の特徴量が効く段にようやく届いた。日次の V ゲートの枠は 1 コンボ 720 秒に調整。
