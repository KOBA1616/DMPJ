# 高速化の検討と提案（対戦AI基盤）

Phase 1〜6 の実測に基づく、高速化の現状・ボトルネックの内訳・対策の詳細。
数値は全てこのVM（共有1.5CPU）でのサガミラー実測。絶対値は環境で変わるが、
律速の構造は変わらない。

**Phase 7 での実施状況（2026-11-24）**: §5 の優先順位を実行した。
1（方策の Rust 埋め込み）と 4（エンコードの Rust 化）を実装し、収集は
3.93 → 6.78 games/s（1.73倍）。2（学習のベクトル化）はトランクの
ゾーン別プーリングをベクトル化し 974 → 1372 decisions/s（1.41倍）。
3（並列収集）は Phase 6 で実施済み。5（エンジン本体）は §3 に分析を
深掘りし、安全な実装方式（版番号キャッシュ）を設計したが、変換トラックと
共用のため全面回帰とセットで別途実施する判断とした（§3.5）。

## 0. エンジンの重い部分を平易に言うと

対戦エンジンは「1手ごとに、場の全部を見直す」作りになっている。1局は
約100回の決定で、その裏では数千回の出来事（カードの移動・攻撃・破壊…）
が処理される。重いのは主に次の3つ。

1. **支払いマナの組み合わせ探し**（カードを出すときの支払い計算）。
   カードを1枚出すには「どのマナをタップすれば金額と色が合うか」を探す
   必要がある。しかも「そもそも出せるか？」の確認だけの場面でも、毎回
   この探し物を始めてしまう。探す前の下準備として、支払いに使える
   マナ全枚と、場のカード全員の「現在の特性」を確認するのが特に重い。
   4局の収集で971回呼ばれ、合計0.54秒（全体の約24%）。
2. **誘発の収集**（「〜した時」という能力の聞き回り）。何か出来事が
   起きるたびに、「この出来事に反応するカードは場にいるか」を全カードに
   聞いて回る。出来事は1局で数千回あるので、聞き回りの総量が効く。
   4局で合計0.46秒。
3. **特性の計算**（カードの今のパワー・色・能力の確定）。カードの特性は
   他のカードの効果で刻々と変わるため、使い回しが効く場面以外は毎回
   計算し直す。4局で8,352回呼ばれた。

なぜ単純に「計算結果を使い回す（キャッシュ）」で済ませないかというと、
特性は場全体の効果の組み合わせで決まるので、古い結果を使い回すと
誤判定の危険がある。このエンジンはカード変換作業とも共用で、1件の
誤判定が変換の正しさに直結する。だから高速化は「速くしても答えが
変わらないことが証明できる場所」から順に手を入れるのが原則で、
Phase 7 で効いたのもその類（処理の場所を移す・往復を消す・同じ計算を
まとめる）である。

## 2. エンコードの Rust 化（詳細）

### 2.1 なぜ必要か

駆動・Rust が駆動・Python より遅い理由は、方策が状態を読むたびに
RustEngine が Python 側の局面ビュー（GameState の複製）を丸ごと作り直す
ことにある（rustcore.RustEngine._view: to_json → state_from_json → Engine 構築）。
決定は1局に約100回あり、その都度この再構築が走る。

エンコード（encode_state / encode_options）が Rust 側の軽い読み口から直接
特徴を作れば、この再構築を消せる。使う読み口の候補:

- `skel_raw()`: ゾーンごとの定義名リスト、タスク、待機中決定などを1回の
  JSON で返す（探索用に既にある）。ただし現状は「タップ状態」「下敷きの数」
  「クリーチャーの現在パワー」などエンコードが使う個札の属性が一部欠ける。
- `zone_ids / zone_names / card_sig`: 区域単位の小さな読み口。呼び出し回数が
  増えると往復コストが戻ってくるので、skel_raw の拡張が本命。

### 2.2 設計

1. dmcore に `features(state)` 相当のメソッドを足すのではなく、skel_raw を
   拡張して個札属性を同梱する: 各ゾーンの札について
   (定義名, タップ, 下敷き数, シールドか否か) を返す形にする。
   既存の skel_raw 利用側（探索）には影響しない追加フィールドとして出す。
2. dmsim/ai/encode.py に `encode_state_skel(skel, player, vocab)` を追加し、
   Python 状態版と「同じ特徴ベクトル」を返すことを契約にする。
3. 検証: ランダムな局面（対戦の途中局面を数百サンプル）で両エンコードの
   出力が完全一致することをテストにする。一致しない特徴があれば、その属性を
   skel 側に足すか、その特徴を両側から落とす（特徴の定義を揃えるのが先）。
4. RustEngine 経由の収集では skel 版を使い、Python Engine では従来版を使う。
   モデルから見れば入力は同一なので、学習・評価の結果は経路に依存しない。

### 2.3 効果と工数の見積り

- 効果: 駆動・Rust の収集が「ビュー再構築なし」になり、対戦ベンチ駆動・Rust
  （8〜10 games/s）と同等以上が見込める。現状の Python 収集（3.9）比で
  2倍前後。ただし §1 のとおり進行の78%はエンジン本体なので、一括API
  （13.8 games/s）には届かない。
- 工数: 中。skel 拡張（Rust）＋エンコード分岐＋一致テスト。リスクは
  特徴の不一致による学習結果の経路依存で、一致テストで封じる。

### 2.4 もう一段先: 方策そのものの Rust 化

エンコードだけでなく推論（モデルの行列演算）まで Rust に入れれば、
Phase 3 の一括APIにモデル方策を載せられる（run_batch の policy に
"model:<重みファイル>" を足す形）。効果は最大（一括の13.8 games/s級で
自己対戦収集）だが、モデルの二重実装と学習側（Python）との重み互換の
維持が要る。torch 化（§5-2）と合わせて検討するのがよい。

### 2.5 Phase 7 での実施結果

§2 と §2.4 をまとめて実装した（dmcore の model.rs、run_batch_model）:
- エンコードと推論を Rust で再実装し、一括APIで「収集＋軌跡記録」まで
  完結させた。語彙の添字は Python の Vocab.ids を渡して一致させる
  （バンドルには別名カードが混ざるため、Rust 側で作ると添字がずれる）。
- パリティ: 対戦途中の局面で Python 版エンコードと完全一致をテストで
  担保（tests/test_rust_model.py）。この検証で Python 側の潜在バグも
  発見した: 静的特徴 is_creature がメソッド参照の誤りで全カード 1.0 に
  なっていた（修正済み。従来モデルは定数特徴で学習していたため無害
  だったが、今後は正しい特徴で学習できる）。
- 軌跡の返却は JSON だと文字列化が律速になるためバイナリ化した
  （メタ情報の JSON ＋ 特徴のバイナリ列）。
- 実測: 収集 3.93（Python 駆動）→ 6.78 games/s（1.73倍）。一括APIの
  13.8 には届かない。残りの差はエンジン進行そのものと、呼び出しごとの
  重み・語彙の再構築で、後者は局数を増やすと薄まる。

### 3.1 _mana_choices（支払いマナの列挙）

- 何をしているか: カードを出すたびに「コストと文明を満たすマナの組み合わせ」
  を最大32組まで列挙する。出す側の面ブースト、場の常在型ブースト、水晶ソウル、
  コスト増減を毎回集めてから組み合わせ探索に入る。
- 重さの理由: (1) 呼び出し回数が多い（プレイ可否判定 _play_options からも
  呼ばれるため、実際に払う回数よりずっと多い）。(2) 常在型ブーストの発生源
  走査が場の全札に対して毎回行われる。(3) 組み合わせ列挙は文明条件の枝刈りが
  あるものの指数的になり得る。
- 対策案:
  a. 発生源の事前索引: mana_boost を持つ定義の集合は既にキャッシュ済み
     （_mb_defns）。さらに「場にある発生源のリスト」を局面の版番号つきで
     キャッシュすれば、走査は差分だけになる。chars の版番号キャッシュ
     （Phase 2 で見送った案）と同型。
  b. 可否判定との分離: 【Phase 7 で確認】可否判定の呼び出し側は既に
     全て limit=1（最初の1組で打ち切り）を渡していた。つまり列挙の
     打ち切り自体は実施済みで、残る重さは列挙ではなく「下準備」
     （マナ全枚の特性確認＋発生源走査）の方だった。対策の主眼は a/c に移る。
  c. 結果のメモ化: (支払う札, コスト, 文明, マナゾーンの指紋) をキーに短命
     キャッシュ。同じターン内の再計算を消す。
- リスク: 結果が変わると方策・探索の挙動が変わる。digest 照合
  （test_rust_engine の lockstep と Python 側の対戦テスト）で選択肢集合が
  同一であることを確認してから入れる。
- Phase 7 の内訳測定（収集4局）: _mana_choices 累積0.54秒のうち自己時間は
  0.14秒で、残りは下準備で呼ぶ abilities（全体で23,795回・0.33秒）と
  chars 系（8,352回・0.34秒）。chars には既にテンプレートキャッシュ
  （定義とゾーンだけで特性が決まる場合の使い回し＋DMSIM_CHECK での
  自己照合）がある。発生源走査の結果は「場の効果の組み合わせ」に依存する
  ため素朴なキャッシュは誤判定の危険があり、やるなら局面の版番号を
  chars の自己照合と同じ作法で検証できる形に限る。

### 3.2 _collect_triggers（誘発の収集）

- 何をしているか: イベントのたびに、発生源候補（バトルゾーンの全ての表向き
  カード＋G・リンクの構成員＋墓地等で機能する zone_trigger のゾーン走査）を
  集め、各発生源の誘発型能力を走査して条件を評価する。
- 重さの理由: イベント数は1局で数千に及び、その都度「場の全札 × 能力」を
  なめる。builtins.any の19万回は主にここの条件評価。
- 対策案:
  a. イベント種別による事前索引: 能力の when（trigger の種別）は定義側で
     静的に分かる。「このイベント種別で発火し得る発生源」だけに候補を絞る
     索引を、場の構成が変わった時だけ更新する。現状も def 単位の絞りは
     一部ある（zone_trigger_defs）が、bz の常在発生源には無い。
  b. 収集結果の再利用: 同一イベントに対する収集は、場が変わらない限り
     同じ。apply_batch の連続イベントでは差分収集にできる余地があるが、
     効果の解決で場が変わるため境界の見極めが要る（難易度高）。
  c. Rust 側は同等の処理を実装済み（第270弾の再帰収集）。Python 側の
     最適化は「Python で回す探索・変換」が対象で、対戦AIの収集は §2 の
     経路が整えば Rust 側に寄せられる。投資先の優先は §2 が上。

### 3.3 _play_options / _can_play_face（出せる札の列挙）

- メインステップのたびに手札の全札 × 面について可否を判定し、その中で
  _mana_choices まで呼ぶ。§3.1-b（存在判定モード）が効く。
- 加えて、可否は「マナゾーンと手札が変わらなければ同じ」なので、
  ターン内の再入では指紋キャッシュが効く。

### 3.4 apply_batch / h_event（移動とイベント処理）

- 1回の移動がイベント発火→誘発収集→SBA→記録の連鎖を起こす。回数そのものは
  ルール上必要な処理で、削れるのは §3.2 の収集と、記録（history）の複製。
  history のレコードは対戦AIではほぼ読まれないが、変換・探索が依存するため
  一律には落とせない。「記録を軽くするモード」はエンジンの互換性を割る
  ため提案としては保留（digest が変わり全テストの前提が動く）。

### 3.5 進め方（エンジン本体）

エンジン本体は変換トラック・探索と共用のため、変更は必ず
(1) digest 照合テスト群（test_rust_engine / test_rust_connect）
(2) 変換側の回帰テスト、の両方を通してから入れる。効果測定は本書 §1 の
物差し（bench_2p と収集プロファイル）で変更前後を比べる。
Phase 7 時点の優先順位は §3.2-a（発生源索引）→ §3.1-a/c（版番号つき
キャッシュ）。どちらも「局面の版番号」を導入し、キャッシュの正しさを
DMSIM_CHECK 型の自己照合で担保する設計が前提になるため、全面回帰と
セットの独立した作業として実施する。

### 3.6 Phase 8 での実施結果（改善案1・2）

設計どおり「指紋（盤面の要約）つきキャッシュ＋check モードでの自己照合」で
実装した。版番号の代わりに盤面指紋を使ったのは、状態の変更箇所が多岐に
わたり、番号の付け漏れが誤判定に直結するため。指紋は内容から計算するので
付け漏れが原理的に起きない。

- 改善案2（誘発側）: _gainable（gain で能力を得る道があるかの走査）を
  「bz・シールドの顔ぶれ＋継続的効果の gain 有無」の指紋でキャッシュ。
  あわせて _static_suppressed を収集1回の中で使い回し（同じ (ctrl, rec)
  では結果が変わらないため）。
- 改善案1（支払い側）: _mana_choices の下準備（常在型 mana_boost と
  mana_all_civs の bz 発生源の収集）を盤面指紋でキャッシュ。scope の
  適用は出すカード依存なので呼び出し側に残した。同一呼び出し内の
  chars_ro の重複もメモ化。
- 正しさの担保: DMSIM_CHECK=1（キャッシュを毎回フレッシュ計算と照合）で
  サガ＋アカシック系など複数デッキの対戦を通し、stale の assert は
  発火しなかった。通常の回帰（Rust との lockstep 含む）も全合格
  （再スタンプ bb181de993bdb67b）。なお回帰の初回は「スタンプ不一致」と
  「新規ワークツリーで dmcore のビルド鮮度チェック（_fresh_build）が
  落ちる」という環境要因で connect テストが落ちたが、再スタンプ＋
  wheel 再ビルドで全合格となり、振る舞いの差異ではなかった。
- 効果（正直な実測）: _mana_choices の自己時間は 0.139 → 0.039 秒
  （4局あたり）と対象の冗長走査は消えたが、収集全体では 4.26 → 4.39
  games/s（同一条件）と誤差の範囲だった。理由: サガミラーでは
  mana_boost / gain の発生源が場にほぼおらず、消した走査がもともと
  軽かった。残る重さは組み合わせ列挙とイベント処理そのもの。
  発生源の多いデッキでは効きが大きい想定だが、未検証。
- 教訓: エンジン本体の残りは「下準備」ではなく「本体の処理量」であり、
  次に効くのは §3.2-a の発生源索引（イベント種別ごとの名簿）か、
  列挙の枝刈りの強化。どちらも意味論に触れるため、digest 照合を
  前提に慎重に進める。

### 3.7 Phase 9 での実施結果（発生源索引: 可能性登録＋付与有効フラグ）

§3.2-a の発生源索引を、リスナー登録の変形で実装した。設計の要点は
「登録は静的に、無効化は作らない」こと:

- **可能性登録**: 発生源の絞り込みは出来事の種別ごとに行う。各定義が
  「自前で持ちうる誘発の種別」を定義から計算して登録する（_pot_kinds）。
  対戦で登場する定義は両デッキ＋トークン・コピーで有限に閉じるため、
  この登録は対戦中ずっと正しく、作り直しや無効化フックが要らない。
- **付与有効フラグ**: 付与で得る能力は登録では表せないので、「今この
  盤面で付与されうる種別」の過大集合を別に持つ（_active_grant_kinds、
  Phase 8 と同じ指紋キャッシュ＋自己照合）。その種別でない出来事は
  付与経由でも発生源になりえない。add_from（他カードの能力の借用）が
  ある盤面では種別を限定できないため索引を使わない（従来動作に落とす）。
- **離脱時誘発（lki）**: 発生源の能力は定義だけで決まるため、可能性登録
  でそのまま絞れる。既存の lki 機構（移動直前の姿の凍結）が凍結リスナー
  に相当する。
- 候補の処理順は従来の走査順のまま（索引は読み飛ばしだけを行う）。
  check モードでは、読み飛ばした発生源を実際に列挙して「その種別の
  誘発が無いこと」を照合する（tests/test_trigger_index.py）。

副次的な発見と修正: _xcache は Rules 共有で、盤面依存キャッシュの鍵に
cid を使うと**別対戦と衝突する**（cid は対戦ごとに振り直される）。
Phase 8 の _gainable と _mana_boost_sources がこの欠陥を持っていた
（同一プロセスで別デッキの対戦を check モードで続けた時に自己照合が
発火して発覚。通常モードでは誤った値が静かに返りうる）。盤面キーには
対戦ごとの名前空間（Engine._gtoken、clone は継承）を前置して修正した。

- 効果（実測、収集4局のプロファイル）: _collect_triggers の累積時間は
  サガ 0.468 → 0.339 秒、天門 0.474 → 0.335 秒（約 -28〜29%）。
  収集全体では 2.33 → 2.24 秒（サガ）・3.53 → 3.48 秒（天門）と

## 4. Colaboratory への並列作業の可否

- 直接の連携（API で Colab を実行させる）は不可。Colab にはプログラムから
  ノートブックを実行する公式 API が無い。
- **ブラウザ操作なら可能（2026-11-24 に Muse のブラウザで実地確認）**:
  Colab の開始ページは Muse のブラウザで正常に開ける。サインインは
  利用者本人がブラウザ上で行う必要があるが、それが済んだ状態で
  「GitHub からノートブック（tools/colab_selfplay.ipynb）を開く→
  ランタイムに接続→最初の2セル（リポジトリ取得・環境確認）を実行」
  まで Muse の操作で完了した。確認できた事実:
  - 非公開リポジトリのノートブックが GitHub 認証なしで開け、ランタイム内の
    git clone も成功した（この検証では。Colab 側の仕様変更で変わり得る）。
  - ランタイムは CPU（Python 3.13、RAM 12.7GB）。**torch 2.14.1+cpu が
    最初から入っている**（CUDA は不可）。このVMでは導入できなかった
    torch が Colab では使えるため、§5-2 の torch 化は Colab が実行場所の
    第一候補になる。
  - 実行前に「Google が作成したものではないノートブック」の警告ダイアログ
    が出る（内容を確認して進める操作が要る）。
  注意点: 長時間の無人実行はアイドル切断・セッション上限のため不安定で、
  対話的に進める用途向き。学習セルの完走確認は今後の課題。
- 現実的な分担: **Colab 用ノートブックをリポジトリに同梱し、利用者が
  Colab で開いて実行 → 結果（学習済みモデルとログ）を Google Drive か
  GitHub に保存 → こちらで取得して検証・続きの学習に使う**。
  同梱物: tools/colab_selfplay.ipynb（本PR）。
- Colab の利点: 無料枠でもこのVMより速い CPU と、torch+GPU が使える。
  特に §5-2（学習のベクトル化/torch 化）と相性がよい。注意点として、
  収集は CPU のエンジンが律速なので GPU は学習側にしか効かない。
  dmcore（Rust）のビルドも Colab 上で可能（rustup+maturin、数分）。
- 代替: このVMの並列収集（Phase 6 実装済み）はコア数に比例するので、
  手元の多コア機で tools/selfplay_train.py --workers N を回すのが
  最も単純なスケール方法。
