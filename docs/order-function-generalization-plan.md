# 順序関数の汎化 実装計画

作成: 2026-11-17（検討ドラフト。本文書は計画であり、実装済み機能の説明ではない）

関連: tools/order_fn.py（順序関数 v2）、tools/turn1_leaf_outcomes.py（順序損失の測定）、
docs/exhaustive-search-saga-report.md §5.6〜§5.7（横断探索と順序関数の実測）。

## 1. 順序関数の役割（前提の確認）

探索は木を辿る作業であり、全部辿れば順序は結果に影響しない。
順序関数が必要になるのは「全部は辿れない／辿り切る前に決めなければならない」
場面だけであり、役割は次の3つに限られる:

1. **発見の速さ**（ターン内探索）: 勝ち線が見つかれば探索は打ち切れるので、
   順序は「勝ちを先に試す並び」を決め、発見までのコストを左右する。
   seen 剪定があるため、どの線が抽象状態の代表になるかにも影響する。
2. **保持の選択**（ターン境界）: beam 幅や frontier 上限で保持しきれないとき、
   順序は「どの未来を残すか」を決める。ここでは順序が結果そのもの
   （キルターンや成否）を変える。実測: hidden では V 順序が最速キルを落とし、
   順序関数 v2 は保持できた。
3. **測定の配分**（候補レベル）: デッキ・部品の候補が多いとき、
   限られた計算をどの候補から測るかを決める（漏斗の優先付け）。

評価関数 V との違い: V は「局面の良さ」を測り、最良線の選択と葉の値付けに使う
（正確さが仕事）。順序関数は「探索の注意の配分」を決める（効率と保持が仕事）。
実測で、V を順序に使うと判断点で平坦で効かず、順序関数を葉評価に使うと
ターン内の誘導が壊れて全敗した。混ぜないことが原則。

不変条件: **順序は除外に使わない**。順序が外れても、辿り切れば結論は変わらない
という性質を守る。保持の打ち切り（役割2）だけは例外的に結果へ影響するので、
そこでは順序の質を実測で担保する。

責務の切り分け（2026-11-17 追記）: 役割2の「どの未来が有望か」という
**判断基準は大局観（MacroPlanner、dmsim/plan/macro.py）の領分**であり、
順序関数の領分ではない。大局観は段階目標の鎖から Plan（現在の段・intent・
探索の幅の目安 budget）を出し、V は計画項（stage_fraction）としてそれを
順位づけに取り込む設計になっている（docs/value-function-design.md §5）。
順序関数はその受け手・実行側であり、「上位 k 件を残す」という機構と、
Plan の外側にある汎用的な生存・接近の特徴だけを持つ。汎化の作業は
「順序関数に戦略判断を持たせる」方向ではなく、「大局観の Plan を
ターン境界の保持に接続し、計画項が実際に順位を動かすか測る」方向に寄せる。
なお試作の横断探索（tools/exhaustive_crossturn.py）は Plan を使っておらず、
順序関数 v2 の進み指標が大局観の代役をしていた。この乖離が本節の出発点。

## 2. 現状（v2）の何がサガ固有か

v2 の辞書式キーは「生存（次のドローで負けない）→ 墓地−山札（循環の進み）→
相手の盾・山札 → 盤面＋マナ → 手札」。

- 「墓地−山札」は墓地循環型ループ（サガ）の勝ち筋に固有の進み指標。
  殴り切り型では墓地はほぼ増えず、このキーは無力になる。
- 「相手の山札の残り」は山札切れ勝ちを狙う型でのみ意味がある。
- 特徴の優先順そのものが「サガでは何が先に効いたか」で決まっており、
  他デッキでの検証は未実施（2026-11-17 時点）。

つまり v2 は「サガの物差しを数値化したもの」であって、汎用ではない。
汎化は (a) 特徴量の置き換え、(b) 優先順の決め方の置き換え、の2層で進める。

## 3. 汎化の方向

### 3.1 特徴量の汎用化（勝ち筋の型に依存しない特徴へ）

候補となる汎用特徴（全て局面から安く計算できること）:

- **相手の敗北接近**: 盾の残り、山札の残り（既存。型を問わず「相手がどれだけ
  追い詰められているか」の下限指標になる）。
- **攻撃圧力**: 自分のブレイカー合計と、相手の盾に対する過剰分。
  殴り型の進み指標はこれと盤面の継続性（除去耐性は近似として体数）。
- **勝利条件への距離**: V の部品である goal_distance（「ゲームに勝つ」常在効果の
  有無と距離）を、V の総和から切り離して特徴として使う。V そのものではなく
  部品単位で使うのが分離の原則に合う。
- **ループ信号**: その局面に至る線でループ証明書に触れたか、ストック量。
  探索中に観測できる汎用信号で、型を問わず「繰り返し構造に入った」ことを示す。
- **キーカードの到達度**: デッキのキーカード（registry のループ部品・
  フィニッシャー候補）について、zone_graph 上で目標ゾーンまでの距離と
  到達済み枚数。デッキごとにキーカードは違うが、測り方は共通にできる。

### 3.2 優先順の出所は大局観の Plan に寄せる

特徴の優先順を順序関数の側で固定しない。「いま何の段を狙っているか」で
効く特徴は変わるので、優先順の出所は大局観の Plan（現在の段と intent）にする:

- 大局観がデッキごとに段階目標の鎖（data/eval/stages/*.yaml、registry の
  combo_sequence）を持ち、局面ごとに現在の段を決め直すのは既存の仕組み。
  保持の順位は「現在の段の充足率（stage_fraction）」を主軸にし、
  汎用特徴（生存・相手の敗北接近）はその補助に回す。
- 型（ループ型／殴り型／置換勝利型）の違いは、鎖の組み方と段ごとの目標で
  表現する。順序関数が型を判定してキーを切り替える形にはしない。
- 段の鎖が無いデッキでは、汎用特徴のみの保守的な順序（生存→相手の敗北接近）
  に落とす。
- 接続の前提として、計画項が保持の順位を実際に動かす大きさかを先に測る。
  既存の実測では plan_w の入れ替わり率は小さく（正規化で数%〜15%）、
  V gate では有意でない結果もある（docs/value-function-design.md 追記）。
  効かないまま接続しても保持は改善しない。

### 3.3 統計版（データから重みを決める）

- データセット: `turn1_leaf_outcomes` の方式で「ターン境界の局面 → その先の
  最速キルターン（または未達）」を複数デッキ・複数シナリオで生成する。
  横断探索の frontier がそのまま教師データになる。
- 学習: 特徴量の重み付き和として順序スコアを定義し、「最速キル局面を
  上位に置けるか」（ランキングの損失）で重みを決める。単純なモデルから始める
  （重みの格子探索またはロジスティック回帰程度）。辞書式はその特殊形として残す。
- 統計版は候補レベル（役割3）にも同じ枠組みで使える（部品・カードの勝率と
  コンボ貢献の集計は、その低次元版）。

## 3.5 実測（2026-11-17）: Plan を保持に接続する実験の結果

§3.2 の方向を先行して測った（詳細は docs/exhaustive-search-saga-report.md §5.9）:

- 既存の生成チェーン（部品集めフェーズ）は、ループ実行中の局面では
  最速キル局面を上位に置けなかった（充足率6・7・9位）。フェーズ不一致が原因。
- 実行フェーズの鎖（実験用に手書き）では最速キル局面が充足率1・2・3位になり、
  beam4 で順序関数 v2 と同一の結果（2ターンキル・同ノード数）が得られた。
- よって本計画の主戦場は §3.1 の特徴量よりも「フェーズごとの鎖の用意」に移る。
  stagegen の生成対象に実行フェーズの鎖を加えることが段3の実質的な中身になる。
  実行フェーズの鎖に必要だった要素は、進み（墓地の育ち）だけでなく
  生存の制約（山札≥2）を段として書けることだった。
- 責務の検討と生成自動化の具体計画は docs/phase-chain-plan.md に分けた
  （結論: 新しい部品は作らず、登録側の中継点抽出・stagegen の入力種別追加・
  鎖ゲートの3点を既存の責務の延長に置く）。

## 3.7 枝切り設計（2026-11-18 の検討で追加）

順序関数は「保持の枝切り」の実行側である。枝切りそのものの設計をここに置く。

- **前提**: 対象は固定シード・無抵抗相手の一人回し探索であり、不完全情報
  ゲームの信念状態探索ではない。相手モデルへの一般化は別のフェーズの話。
- **目的の限定**: 枝切りは「全部は展開できない空間で有限の計算予算を
  配分する賭け」であり、目的は (a) 発見（キル手順・鎖の材料を現実的な
  時間で得る）と (b) 規模（母集団スキャンを日単位に収める）に限る。
  証明には使わない: 枝切りした探索からは勝ちなしを言わず、全保持だけが
  証明の金標準。枝切りは宣言付きの代替手段として扱う。
- **モード分離**: 発見モードは代理指標による集中（上位 k)、材料集め
  モードは多様性の確保（生特徴の層別・部分木単位の保持など）を旨とし、
  run の設定にモードを宣言して記録に残す。材料の偏りは鎖の偏りに直結
  するため、材料集めで発見モードの集中を流用しない。
- **定量目標**: (1) コストは平均でなく裾（重いシード）で見る、
  (2) 保持の質はラベル付きケースでのキルターン再現率、(3) 材料の
  歩留まりは exact 局面の残存率（exact は局面単位で伝播させる:
  chain_label 実装済み）、(4) 正直さ（capped と落としたキーの記録）、
  (5) 再現性（下記の順序非依存）、(6) 監査可能性（落下監査: 落とした
  局面の標本を事後展開し、dist 有限だった割合を推定する）。
- **順序非依存（要件）**: 保持選択は候補集合の「内容だけ」の関数で
  なければならない。選択規則はスコア列＋局面キーを最終タイブレークと
  する全順序で定義し、上位 k を取る。到着順のカット（chain_label の
  `nxt_keys[:cap]`）はこの要件に反するので、方針の実装時に全順序化する。
  無作為な間引きが要る場合はキーのハッシュによる決定的サンプリングで
  代替する。これにより並列化・分割再開・機械の違いで保持集合が変わらない。
- **集中と多様性は配合で扱う**: 実行時に相関を見て切り替える方式は、
  切替の入力と記録の規定ができるまで採らない。配合比（例: 上位 k に
  多様性枠を加える）をオフラインの相関測定で調整する。
- **教師データの作り方（§3.3 の具体化）**: 0ターン目 exact の量産は
  しない。主軸は (a) 中盤スナップショット（実プレイで到達した局面を
  凍結し、短いホライズンでラベル付けする。安く、保持判断の実分布に
  合う）と (b) 階層化ラベル（キル記録の経路上の局面が持つ上限ラベル
  「dist ≤ 残りターン」）。負例の規律: dist=∞ の負例は exact なものに
  限る。回し損ねた局面を ∞ として学習させない。代理指標が高く評価
  したが exact には ∞ だった局面（ハードネガティブ）を優先的に含める。
- **学習モデルの段階**: §3.3 の統計版（線形）を基準として先に確立する。
  小規模 Transformer（カードをトークン化し相互作用を学習する）は
  挑戦者として同じ物差しで測り、デッキ単位ホールドアウトで線形に
  勝った場合のみ採用する。seed24 の候補374件の順位診断は疎通確認で
  あって採用ゲートではない。本体の依存は PyYAML のみに保ち、学習は
  道具側、推論は重み（.npz）を NumPy でバッチ実行する形に分離する。
  モデルの版数は設定ハッシュに含め、どのスコアで切ったかを記録する。

## 4. 検証プロトコル（過適合を防ぐ）

- **デッキで分ける**: 校正用（サガ系）と検証用（サガ以外。テンモン等の別系統の
  ループ、殴り型デッキ）を分け、検証用では特徴も優先順もいじらない。
- 物差し: beam 幅を絞った条件で、(1) 最速キルの保持率、(2) キルターン、
  (3) ノード数、(4) 全滅率（保持した線が全て死ぬ割合）。frontier（全保持）を
  正解として比較する。
- 判定: 検証用デッキで v2（サガ校正のまま）より悪ければ、その特徴は
  サガ固有と確定して 3.1/3.2 の置き換え対象にする。校正用だけで良い結果は
  「汎化した」とは言わない。

## 5. 段階計画

1. 段1: 特徴量の実装（3.1）。order_fn を「特徴量の辞書を返す層」と
   「キーに変換する層」に分け、特徴の追加・入替ができる形にする。
2. 段2: 検証プロトコルの自動化。シナリオ＋デッキのケース集で、
   順序方式×beam幅の表を定型コマンドで出せるようにする。
3. 段3: 型による優先順の切替（3.2）。registry の情報が要るので、
   フィニッシャー自動特定の実装と連動させる。
4. 段4: データセット生成と統計版（3.3）。段2のケース集をそのまま
   教師データ生成に使う。
5. 段5: 検証用デッキでの判定（4）。結果を報告書に追補する。

## 6. 未決事項

- 型判定の材料を registry にどう持たせるか（フィニッシャー計画の
  「registry を正本にするか生成物にするか」と連動）。
- 統計版のモデル規模: 重み付き和で足りるか、特徴の交互作用が要るかは
  データセットを作ってから判断する。
- 順序関数の適用範囲を候補レベル（役割3）まで広げる時期。
  ターン境界（役割2）で汎化が確認できてからにする。
- 学習スコアラが使う局面情報の範囲。鎖の抽出は公開情報のみという
  規約（§3.7 の教師データでも山札は残り枚数のみ）だが、探索内部の
  保持判断は完全な局面を見ている。学習モデルに山札の構成・順序まで
  使わせるかを、規約と一貫する形で決める。
- 集中と多様性の配合比の決め方（§3.7）。相関の測定結果を配合比に
  写す規則が要る。
