# ディスク常駐・分割実行の設計方針

保持型探索（exhaustive_crossturn の frontier）を、長時間・大規模に回すための
実行方式の設計。対象は「局面を大量に保持する探索」のメモリと中断への耐性で、
探索そのものの速さや総作業量は変えない（高速化ではない）。

## 解く問題

2026-11-17 の実測で判明した制約:

- 保持局面そのものより、1局面のターン内展開が集める葉の蓄積がメモリを殺す
  （葉のストリーミング化で対処済み）。
- それでも保持局面の総量はターンごとに増え、メモリ常駐のままでは上限がある。
- 実行環境の再起動で十数分級の実行が中断される。中断されると、その実行の
  作業は全て失われる（進捗ログだけが残る）。

## 設計方針

1. **局面の実体はディスクに置く。メモリは作業場。**
   保持局面・次ターン候補は、生まれたらデータとして保存し、メモリからは落とす。
   メモリに常駐するのは「いま展開している1局面」と、候補のキーとスコアだけ。
   局面のアクセスは「1回書かれ、1回展開され、捨てられる」が基本で、
   ランダムアクセスはほぼ無いため、ディスク常駐と相性が良い。
2. **完全性は digest 照合で担保する。**
   保存は記録（手順ログ）の再生ではなく、局面データ（GameState＋手順ログ）
   そのものの直列化で行う。読み込み時に digest を保存時の値と照合し、
   1つでも一致しなければ再開・継続をしない。
   記録＋再生は「見つけたキルの証明」のための通貨であり、作業状態の保存とは
   用途を分ける。
3. **書き込みは一度きり。キーは fast_key。**
   候補集合に入った局面はその後変更されない（展開は常に複製側で起きる）ため、
   同じキーのデータは二度書かない。チェックポイントの本体は、
   キーの並びと進捗を記した小さな「目録」だけになる。
4. **判定の正直さはフラグの持ち越しで担保する。**
   実行を分割しても、打ち切り（capped / truncated / 予算・メモリによる中止）の
   フラグは目録で全チャンクに持ち越す。全チャンクを通して打ち切りが
   無かった場合だけ no-kill を名乗れる。kill は従来どおり記録＋再生検証。
5. **設定が違えば再開しない。**
   目録に設定ハッシュとエンジン版を埋め込み、再開時に照合する。
   別の探索の途中状態を掴んで、別物の判定を出す事故を防ぐ。
6. **安全弁は別軸として残す。**
   局面毎のノード予算、葉上限（当たれば truncated）、総ノード予算、
   メモリ上限の監視は、ディスク化しても残す。ディスク化が解くのは
   「保持の総量」と「中断」であって、1局面の爆発はこれらの担当。

## 仕組み

```
起動1              起動2              起動3
┌─────────┐      ┌─────────┐      ┌─────────┐
│探索      │      │目録から  │      │目録から  │
│局面 kまで│      │再開      │      │再開〜完了│
└────┬────┘      └────┬────┘      └────┬────┘
     │                 │                 │判定
     ▼                 ▼                 ▼
┌─────────────────────────────────────────────┐
│ 状態ストア（ディスク）: fast_key → 局面データ │
│   GameState ＋ 手順ログ、書き込み一度きり     │
│ 目録: 保持キーの並び・スコア・進捗            │
│   (ターン/次の局面/累計ノード)・              │
│   打ち切りフラグ・設定ハッシュ・エンジン版    │
└─────────────────────────────────────────────┘
```

1局面のライフサイクル:

1. 葉から次ターン候補が生まれる（メモリ上の一時的な実体）。
2. キー（fast_key）と保持スコアを計算し、データを保存してメモリから落とす。
   候補集合に残るのはキーとスコアだけ。
3. ターン終了時にスコア順で保持を決める（従来どおり）。残らなかった候補の
   データは掃除で消す。
4. 次ターン、その局面の番になったら読み込み、digest を照合してから展開する。
   展開が終われば実体は捨てる（データは残るが、次に必要になることはない）。

分割の単位はノードチャンク（例: --chunk-nodes 500000）とし、チャンクを
使い切ったら目録を書いて正常終了する。再開は目録のある場所から、
何回でも、別のプロセス・別のマシンでもできる。

## 前提と検証

唯一の前提は **局面データの往復（直列化→復元）が完全であること**:

- GameState は純データ（dataclass）で、乱数状態も int フィールドとして
  含まれる。digest は全フィールドの asdict から作られるため、
  復元後の digest 一致は「未来を左右する全てが一致した」ことの強い証拠になる。
- ただし前提は実験で証明してから使う。試験項目:
  - A: 実局面（仕込み局面の frontier、実デッキの対局途中）で、
    復元後の digest と fast_key が保存時と一致する。
  - B: 復元した局面から同じ方策で継続すると、元の局面からの継続と
    全決定点の digest 列が一致する（分岐チェックと同じ型）。
  - C: 復元した局面（キル到達時）から作った記録が strict 再生を通る。
  - D: 直列化・復元・照合のコスト（ms/局面、バイト/局面）を実測し、
    展開コストに対して無視できる水準か確認する。
  - 条件には COW 有効（探索系ツールの既定）を含める。
- 往復が壊れる場合はこの方式は採らず、記録再生によるチェックポイントに
  落とす（再開コストが高いため、チャンクを大きくして再開回数で調整する）。

### 検証結果（2026-11-17、前提は成立）

対象: prep シナリオ・doom_e（seed24）・本家 saga（seed6）の対局から採取した
決定点の局面 30件（手順ログ 0〜27件、COW 有効）。直列化は pickle
（GameState＋手順ログ）。

- A: **30/30**（digest・fast_key とも保存時と一致）
- B: **30/30**（同一方策で最大60決定まで継続し、全決定点の digest 列が一致）
- C: **通過**（既存のキル記録の最終局面を往復させ、作り直した記録が
  strict 再生を通過、digest 一致）
- D: 保存 0.28ms／復元 0.56ms／digest 照合 1.87ms（いずれも平均・1局面あたり）、
  データ量は平均 13.1KB/局面。往復＋照合で約2.7ms/局面であり、
  局面の展開コスト（数百ms〜）に対して無視できる。1万局面で約130MB。

標本はサガ系3系統に限られる。他系統の局面でも仕組みは同じ（純データ＋
全フィールド digest）で、万一壊れる局面があっても読み込み時の digest 照合が
検出して停止する（静かに壊れたまま進むことはない）。

## 実装状況（2026-11-17）

crossturn に `--store-dir` / `--resume` / `--chunk-nodes` として実装済み。
等価性検証: deck saga seed1 T2（no-kill・238ノード・保持 [9, 130]）は
単一実行・チャンク分割（50ノード×4回）ともメモリ常駐と一致。
prep seed1 T2 frontier・上限なし（kill・2ターン・91,874ノード・
保持 [131]、capped/truncated とも false）も単一実行・チャンク分割とも
一致し、キル記録は strict 再生を通過した。

注意: チャンク判定は局面の境界でのみ行う。prep の例ではターン2の
最初の局面の展開だけで 91,270 ノード（全体の 99%）を消費してキルを
含んでいたため、チャンク 5,000 でも分割は発生しなかった。1局面の
展開コスト自体は局面毎ノード予算・葉上限・メモリ監視が受け持つ。

## 限界

- 総作業量は減らない。終わらない探索は、分割しても終わらない。
  終わる見込みの判断はノード総量の実測から別途行う。
- 読み込んだ局面同士では COW の共有は効かない。ただし常駐方式では
  実体を読むのは1局面ずつなので、保持全体への影響は小さい。
- ディスク容量はケースの規模に比例する。ターン毎の掃除で抑える。
- 直列化の形式は Python の pickle を想定し、目録のエンジン版・設定ハッシュで
  版の異なる再開を遮断する。
